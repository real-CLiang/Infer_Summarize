### 0.2 横向：时间轴 × 空间轴（把 L1、L2、L3 合起来看）

```
        ┌───────────────────── key = 指纹 × 坐标（L3）─────────────────────┐
        │  block_hash（vLLM 算，scheduler 只算一次，全 rank 共用）          │
        │      ×  KeyMetadata（model/dcp/head_or_tp/pp/group/role/family）  │
        └───────────────────────────────┬──────────────────────────────────┘
                                        │ 贯穿全部 8 个钩子
   时间轴（L1）                          空间轴（L1 四层）
   ① get_num_new_matched_tokens ───────► Scheduler + Backend.exists（L2）
   ② update_state_after_alloc    ───────► Scheduler（记录命中）
   ③ build_connector_meta        ───────► Scheduler → ReqMeta → Worker
   ④ bind + register_kv_caches   ───────► Worker → Backend.register_buffer
   ⑤ start_load_kv               ───────► Worker 线程 + Backend.get
   ⑥ forward（引擎）             ───────► attention 读本地 KV
   ⑦ save_kv_layer / wait_for_save ─────► Worker 后台线程 + Backend.put
   ⑧ get_finished                ───────► Scheduler（释放 block、统计）
```

**读法**：竖着是"一个请求的一生"，横着是"这活归谁干"，斜插的那根线是 key。

## 1. 六条主线（能背下来就够用）

| # | 主线 | 一句话 | 出处 |
|---|---|---|---|
| 1 | **收益边界** | 池化省的是 prefill 的算力（TTFT 与 P 节点吞吐），**不省 decode 的显存**；无重复前缀时是净亏 | L0 §6.2 |
| 2 | **key = 指纹 × 坐标** | hash 管"是不是同一段 token"，坐标管"是不是同一份字节"；少一个维度就是**静默错数据** | L0 §5、L3 §1-2 |
| 3 | **命中 = 连续 + 对齐 + 三刀** | 沿链从 h0 查、第一个断点就停、再压到 granularity 倍数、最后过三刀（不能全命中 / EAGLE 留块 / 粒度） | L1 §2.5-2.6、L3 §4 |
| 4 | **传输 = 二维地址** | 外层是 key、内层是"这个 key 散成几段"；`addr = base + block_id × stride + 段内偏移` | L2 §4.2 |
| 5 | **Backend = 6 + 3 + 14** | 两家 API 不一样不是风格，是**对象语义（藏地址）vs 地址语义（给地址）** | L2 §3、§5 |
| 6 | **失败策略看位置** | 越靠近"决策"越严（查询 fail-closed），越靠近"动作"越松（写回 fail-open，搬运可 recompute） | L2 §4.3、L3 §4.3 |

**六条的连接方式**：第 1 条决定"值不值得做"，第 2 条决定"对不对"，第 3 条决定"能省多少"，第 4 条决定"怎么搬"，第 5 条决定"存哪里"，第 6 条决定"坏了怎么办"。

## 2. 八钩子 × 四层 对照表（查细节用）

| 阶段 | 钩子 | Scheduler | Worker | Backend | 关键概念 |
|---|---|---|---|---|---|
| 查命中 | `get_num_new_matched_tokens` | 生成 key、逐块 `exists`、对齐、三刀 | bulk 时经 ZMQ 由 rank0 回答 | `exists` / `batch_is_exist` | 指纹×坐标、granularity |
| 定需求 | `update_state_after_alloc` | 命中信息挂到 RequestTracker | — | — | 日志命中数 ≤ 理论值 |
| 下发 | `build_connector_meta` | 产出 `ReqMeta` | `bind_connector_metadata` | — | 调度粒度 ≠ 对象粒度 |
| 注册 | `register_kv_caches` | — | `register_buffer(ptrs, lens)` | 登记（pin）| **没注册 = 一次都搬不了** |
| 搬入 | `start_load_kv` / `wait_for_layer_load` | — | 线程 + per-layer Event | `get` / `batch_copy(G2L)` | **load 阻塞** |
| 计算 | forward | — | — | — | 至少真算 1 个 token |
| 搬出 | `save_kv_layer` / `wait_for_save` | — | 后台发送线程 | `put` / `copy_put`+`commit` | **save 异步** |
| 收尾 | `get_finished` | 释放 block、统计 | 报完成 | — | 池子是可失败的加速器 |

## 3. 症状 → 先去哪个文件

| 症状 | 第一个该看的地方 |
|---|---|
| 命中数是 0 / 比预期少 | `pool_scheduler.get_num_new_matched_tokens`（先看走哪条分支）→ 再查三刀 |
| 换 TP / 换 block_size 后命中归零 | L3 §5 `infer_tp_mismatch_info`、`hash_block_size` |
| 命中数对，但加载失败 | `pool_worker.lookup` / recv 线程 / `kv_load_failure_policy` |
| **精度异常或乱码，且不报错** | 优先怀疑 **key 漏维度**（L3）或 **buffer 没注册**（L2 §4.1） |
| 传输慢、TTFT 反而变差 | Backend 的 `put/get` 实现 + layerwise 预取配置 |
| 启动就报配置错 | `AscendStoreConnector.__init__` 的参数互斥校验 |
| layerwise 下 graph 抓取失败 | `requires_piecewise_for_cudagraph` 返回 `use_layerwise` |
| 日志出现 `MMC_UNMATCHED_KEY` | 试图覆盖 Mooncake 已提交对象 → 检查 save 前的 `exists` 过滤 |

## 5. 已经建立的边界（别越界理解）

- **池化不省显存**：decode 的 KV 必须驻留 device；省显存的那条线是 KVPP。
- **池化不保证正确性**：它是"可失败的加速器"，`recompute` 是它的定位声明。
- **半块不存在**：命中判定只在块边界上；能带尾块的是"传输"，不是"命中"。
- **换后端 = 换 key 空间**：两个池子的数据互不认识。
