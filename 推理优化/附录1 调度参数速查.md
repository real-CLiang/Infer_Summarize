## 8. 附录：调度参数速查
### 8.1 五层总览
```text
部署层   data_parallel_size / pipeline_parallel_size / kv_role / num_speculative_tokens
KV 层    gpu_memory_utilization / block_size / kv_cache_dtype / enable_prefix_caching / watermark
step 层  max_num_batched_tokens(B) / max_num_seqs(S) / enable_chunked_prefill /
         long_prefill_token_threshold / policy / async_scheduling / scheduler_cls
请求层   max_model_len(L) + 请求自身的 prompt 长度与 max_tokens
```
作用域：请求层管“一条请求能活多长”，step 层管“每一步算多少”，KV 层决定“池子多大”，部署层决定“实例形态”，Ascend 扩展层决定“用哪种调度策略”。
### 8.2 请求层与 step 层
| 参数 | 含义 | 常见默认 | 主要影响 |
| --- | --- | --- | --- |
| `max_model_len`（L） | 单条请求序列总长上限（prompt + 生成） | 模型 `max_position_embeddings`；`-1` 按显存自动拟合 | 决定 block table 宽度与单条请求最坏 KV；prompt + max_tokens 超限直接拒绝 |
| `max_num_batched_tokens`（B） | 一个 step 内全部请求的 token 数上限 | 8192 | 调大：TTFT↓、TPOT 抖动↑、buffer 变大；调小：TTFT↑、step 数↑ |
| `max_num_seqs`（S） | 一个 step 内请求条数上限（名义并发） | 256 | 调大：吞吐↑、KV 压力与抢占↑；调小：吞吐↓、延迟稳 |
| `enable_chunked_prefill` | 长 prompt 是否允许拆到多个 step | v1 默认开 | 关闭后必须 `B ≥ L`，否则长 prompt 报错 |
| `long_prefill_token_threshold` | 单请求一步最多 prefill 的 token 数，0 为不限 | 0 | 调小：长 prompt 切更碎、TTFT↑；调大：更占预算、他人 TPOT↑ |
| `policy` | waiting 队列策略：`fcfs` / `priority` | `fcfs` | `priority` 需请求带优先级；ShortRequestFirst 强制要求 fcfs |
| `async_scheduling` | CPU 调度与 NPU 执行重叠，状态滞后一步 | False | 藏掉调度开销；部分 Ascend 调度器要求 V2 runner |
| `scheduler_cls` | 使用哪个调度器实现 | 上游 `Scheduler` | Ascend 按 `scheduler_config` 覆盖，映射见第 4 节与 8.5 |
> 代码中的 `max_num_scheduled_tokens` 即 B，`token_budget` 的初值来自它。
### 8.3 KV 层
| 参数 | 含义 | 常见默认 | 约束 |
| --- | --- | --- | --- |
| `gpu_memory_utilization` | 可用于 KV 的显存比例 | 0.9 | 越大池越大、并发越高，activation 余量越小 |
| `block_size` | 每个 block 容纳的 token 数 | 上游 16；Ascend 常为 128（[refresh_block_size](vllm_ascend/utils.py#L1423)） | 影响 block table 宽度、prefix cache 粒度、碎片率 |
| `kv_cache_dtype` | KV 量化类型 | auto | 量化省显存、提并发，有精度风险 |
| `enable_prefix_caching` | 复用公共前缀的 KV | v1 默认开 | 省 prefill，增加 block 管理开销 |
| `watermark` | KV 分配预留水位 | 0.01 | 可用 block ≈ P × (1 − watermark) |
| `num_gpu_blocks_override` | 手动指定 block 数 | 无 | 调试用，绕过自动探测 |
### 8.4 部署层
| 参数 | 与调度的关系 |
| --- | --- |
| `tensor_parallel_size` | 序列并行要求 B 为 `tp × pcp` 的倍数，框架自动上对齐（[ascend_config.py:819](vllm_ascend/ascend_config.py#L819)） |
| `pipeline_parallel_size` | 引入 `throttle_prefills` / 动态 chunk PP，prefill 需按 stage 配速 |
| `data_parallel_size` | `enable_balance_scheduling` 与 DyntraLB 的前提 |
| `kv_role` | `kv_producer`（P）/ `kv_consumer`（D），决定哪些调度器可用 |
| `num_speculative_tokens` | decode 每请求每步消耗 `D = 1 + num_spec` 个 token |
| `max_cudagraph_capture_size` | 必须覆盖 `min(B, S × D)`；Ascend 默认取 `min(S × D, 512)`（[platform.py:1732](vllm_ascend/platform.py#L1732)），不足会告警（[utils.py:1279](vllm_ascend/utils.py#L1279)） |
### 8.5 Ascend 扩展层（`additional_config.scheduler_config`）
字段定义见 [SchedulerConfig](vllm_ascend/ascend_config.py#L1630)，调度器选择逻辑见 [platform.py:1457](vllm_ascend/platform.py#L1457)。
| 配置项 | 字段（默认值） | 作用 |
| --- | --- | --- |
| `enable_balance_scheduling` | `False` | 全局准入闸门，仅 PD-mixed |
| `recompute_scheduler_enable` | `False` | D 节点 KV 不可用时重算 prefill，仅 `kv_consumer` |
| `short_request_first_config` | `enabled=False`、`threshold=256`、`long_max_wait_ms=0`（[定义](vllm_ascend/ascend_config.py#L1569)） | 短请求优先 + 老化，缓解队头阻塞 |
| `profiling_chunk_config` | `enabled=False`、`smooth_factor=1.0`、`min_chunk=4096`、`need_timing=None`、`max_fit_chunk=30`（[定义](vllm_ascend/ascend_config.py#L1490)） | profile 拟合延迟模型，动态决定 chunk 大小 |
| `batch_job_sched_config` | `enabled=False`、`max_jobs=20`、`reserve_margin_blocks=2`、`reserve_max_blocks=8`、`low_available_tokens_threshold=4096`、`short_decode_token_threshold=32`（[定义](vllm_ascend/ascend_config.py#L1529)） | 离线 batch：LPT + KV 预留 |
| `dyntra_lb_config` | `enabled=False`、`mode="dynamic"`、`start_step=250`、`end_step=-1`、`bubble_threshold=5.0`、`long_req_block_threshold=700`、`dynamic_max_step=256`（[定义](vllm_ascend/ascend_config.py#L1591)） | DP 内 decode 负载均衡（admit/keep/pause，不迁移请求） |
### 8.6 核心不等式
1. `prompt_len + max_tokens ≤ L`
2. `Σ t_i ≤ B`
3. `N ≤ S`
4. `N_decode ≤ ⌊B / D⌋`（推测解码下 token 预算先满，S 名义够也会被截断）
5. 关闭 chunked prefill 时 `B ≥ L`
6. `S × ceil(L / (block_size × dcp)) ≤ P × (1 − watermark)`
7. `capture_size ≥ min(B, S × D)`
8. `B % (tp × pcp) == 0`（Ascend 序列并行会自动上对齐）
9. `B ≥ profiling_chunk_config.min_chunk`（默认 4096）
10. `B ≤ 1024` 才启用 MLAPO 融合 MLA prefill（[attention/utils.py:46](vllm_ascend/attention/utils.py#L46)）
第 6 条最容易被低估：**最坏 KV 需求 = S × L × 每 token KV**，而实际 KV ≈ S × 平均上下文。S=256、L=32k 时，即使平均上下文只有 4k，启动校验也可能把实际并发压到几十。

| 规则 | 依据 |
| --- | --- |
| 同一实例只有一个 `scheduler_cls`；`recompute` 可与 `dyntra` 组合 | [platform.py:1209](vllm_ascend/platform.py#L1209) |
| `short_request_first` 不能与 `batch_job_sched` 同时开 | [platform.py:1127](vllm_ascend/platform.py#L1127) |
| `short_request_first` 要求 `policy=fcfs`，且不能在 D 节点 | [platform.py:1122](vllm_ascend/platform.py#L1122) |

### 8.8 调参顺序与模板
调参顺序：先按业务 P99 定 `max_model_len`；再用 `gpu_memory_utilization` / `block_size` 定 KV 池 P；然后用 `S × L` 估算最坏 KV，确认 S 可达；最后单独调 B，看 TTFT / TPOT 拐点；策略类开关（ShortRequestFirst、profiling chunk、balance、dyntra）最后叠加。
| 模板 | B | S | L | 其他 |
| --- | --- | --- | --- | --- |
| 在线低延迟 | 4096–8192 | 32–128 | 业务 P99 | `long_prefill_token_threshold` 取小值保 TPOT |
| 在线均衡 | 8192–16384 | 128–256 | 业务 P99 + 余量 | 开 prefix caching |
| 离线吞吐 | 16384–32768 | 尽量大 | 按最长样本 | `batch_job_sched_config.enabled=true` |
### 8.9 现象 → 先查哪个参数
| 现象 | 优先检查 |
| --- | --- |
| 首 token 慢、后续正常 | `L` 是否过大、`B` 是否过小、chunk 是否过碎 |
| TPOT 周期性尖刺 | `B` 过大导致 prefill 混入、是否发生抢占（看 `num_preemptions`） |
| 实际并发远低于 `S` | KV 池不足：`L` 太大、`gpu_memory_utilization` 太低、KV 未量化 |
| 长 prompt 直接报错 | 关闭了 chunked prefill 且 `B < L` |
| 吞吐上不去但延迟很好 | `S` 或 `B` 太小，或 `capture_size` 未覆盖 decode batch |
| 开启某特性后启动失败 | 查 8.7 互斥表，通常是策略组合冲突 |
