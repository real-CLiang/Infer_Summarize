## 0. 三十秒版本

调度器**不做任何计算**。它每毫秒级跑一次（一个 *step*），只回答四个问题：

1. 这一步哪些请求上 NPU？
2. 每个请求算多少个 token？
3. 按什么顺序？
4. 显存不够时牺牲谁？

答案打包成一份 `SchedulerOutput` 交给 ModelRunner 执行。**调度的 bug 几乎从不表现为数值错误，而是表现为延迟抖动、吞吐上不去、请求被饿死、OOM。**

---

## 1. 第一性原理：为什么需要调度器

### 1.1 单条请求的困境

一条请求做 decode 时，每个 step 只算 **1 个 token**。矩阵乘退化成矩阵-向量乘（GEMV），算力单元大面积空转，瓶颈在**读 KV cache 的带宽**上。

结论：**推理的算力是靠 batch 撑起来的**，不是靠单条请求。

### 1.2 但 batching 不是免费的

| 代价 | 说明 |
| --- | --- |
| 延迟耦合 | 一个 step 的耗时由 batch 里最慢的那个请求决定 |
| 显存 | KV cache 随 `batch × 上下文长度` 线性增长 |
| 形状不一 | 每请求长度不同，padding 浪费算力（vLLM 用压平布局规避，但 kernel 仍受最长者影响） |

### 1.3 请求是流式到达的

A 在跑、B 刚来、C 已经结束。如果 batch 在启动时定死，要么等（延迟爆炸），要么浪费（B 得等 A 跑完）。

于是有了 **continuous batching**：**每个 step 重新组一次 batch**，请求一结束立刻腾出位置给新请求。这是 vLLM 的起点。

### 1.4 KV cache 让问题变成"内存管理"

一个请求的 KV 大小 ≈ `2 × 层数 × KV头数 × head_dim × token数 × dtype`。它会**随生成不断增长**，而且无法预知何时结束。

于是显存成了硬约束：**不是你有多少算力就能塞多少请求，而是你有多少 KV block。** 这就是"抢占（preemption）"存在的原因。

### 1.5 由此得到调度器的定义

> 调度器 = 在「算力预算」「KV 显存」「并发槽位」三个约束下，
> 每个 step 重新做一次资源分配决策的程序。它只操作元数据，不碰张量。

## 2. 词汇表（先认全这 12 个词）

| 词 | 一句话解释 | 代码里对应 |
| --- | --- | --- |
| **step / iteration** | 一次 forward，处理一个 batch 的 token | `current_step` |
| **prefill** | 把 prompt 的 token 一次算完，产出 KV | `num_computed_tokens < num_prompt_tokens` |
| **decode** | 用已有 KV 算下一个 token | 同上取反 |
| **chunked prefill** | 长 prompt 切成几块，分多个 step 算 | `long_prefill_token_threshold` |
| **KV block** | KV cache 的最小分配单位，通常 128 token | `block_size`、`allocate_slots` |
| **preemption** | 显存不够时踢掉某个请求，释放它的 KV | `_preempt_request` |
| **recompute** | 被抢占的请求回来后重算（v1 的唯一恢复方式） | 重算即前缀重跑 |
| **prefix caching** | 相同前缀的 KV 直接复用，不重算 | `cached_tokens`、`get_computed_blocks` |
| **token budget** | 一个 step 最多算多少 token | `max_num_batched_tokens` |
| **TTFT** | Time To First Token，首 token 延迟 | 指标 |
| **TPOT / ITL** | 每 token 间隔（decode 阶段） | 指标 |
| **goodput** | 满足 SLO 的请求比例（比吞吐更贴近业务） | 指标 |

三个最容易混淆的计数：

| 名字 | 含义 |
| --- | --- |
| `num_computed_tokens` | 这个请求**已经算过**多少 token |
| `num_scheduled_tokens` | **这一步**给它安排了多少 token |
| `cached_tokens` | 其中有多少是**前缀缓存命中**、不用真算的 |

## 3. 三个预算、两个目标、一个决策

### 3.1 三个预算

| 预算 | 来源 | 花完的后果 |
| --- | --- | --- |
| 算力（token 数） | `max_num_batched_tokens` | 这步装不下了，请求等到下一步 |
| 显存（KV block） | block pool 空闲块数 | 分配失败 → 抢占或拒绝准入 |
| 并发槽位 | `max_num_seqs` | running 队列满 → waiting 排队 |

还有两个"隐形预算"，只在特定场景生效：多模态的 **encoder cache**、LoRA 的 **max_loras**。

### 3.2 两个目标

| 目标 | 指标 | 被谁伤害 |
| --- | --- | --- |
| 延迟 | TTFT、TPOT | batch 太大、prefill 混进 decode、抢占重算 |
| 吞吐 | tokens/s、goodput | batch 太小、频繁抢占、调度开销 |

二者永远互相拉扯，**没有唯一最优解，只有针对负载形态的取舍**。这就是"调度策略"这个词的全部含义。

### 3.3 一个决策

在所有策略变体里，变的永远只有三个答案：**准入谁 / 算多少 / 牺牲谁**。

## 4. 一个 step 的完整决策流程

```
        新请求 ──► waiting 队列（FCFS / 优先级 / 分车道）
                        │
   ┌────────────────────┴─────────────────────────────────┐
   │ schedule() 每个 step 执行一次                          │
   │                                                      │
   │  ① 备预算                                            │
   │     token_budget / input_budget / encoder_budget      │
   │                                                      │
   │  ② 扫 running（优先，因为已投入且 decode 很便宜）        │
   │     n = 还欠多少 token                                │
   │       = num_tokens_with_spec - num_computed_tokens    │
   │     n = min(n, long_prefill_token_threshold, 预算)     │
   │     allocate_slots(n) ── 成功 → 记账，预算 -= n         │
   │            │                                          │
   │            └─ 失败 → 抢占最晚到达的请求                 │
   │                     （释放 KV，回 waiting，将来重算）    │
   │                                                      │
   │  ③ 扫 waiting（只在没发生抢占时）                        │
   │     查前缀缓存 → 能跳多少跳多少                          │
   │     预算不够 → 切一块（chunked prefill）                 │
   │     检查 max_num_seqs / LoRA / encoder cache / 远端 KV  │
   │                                                      │
   │  ④ 组装 SchedulerOutput（+ KV connector 元数据）        │
   └──────────────────────────────────────────────────────┘
                        │
                        ▼
              ModelRunner 执行 → 采样 → update_from_output
                        │
                        └─ 释放完成的请求、回填 token、下一 step
```

### 4.1 伪代码（去掉所有优化）

```python
def schedule():
    token_budget = self.max_num_scheduled_tokens          # 本步总预算
    num_scheduled, plan = {}, {}

    # 阶段一：已经在跑的请求
    for req in self.running:
        if token_budget == 0:
            break
        n = req.num_tokens_with_spec - req.num_computed_tokens
        n = min(n, token_budget)
        blocks = self.kv_cache_manager.allocate_slots(req, n)
        while blocks is None:                              # 显存不够
            victim = self.running[-1]                      # FCFS：踢最晚来的
            self._preempt_request(victim)                  # 释放 KV，回 waiting
            blocks = self.kv_cache_manager.allocate_slots(req, n)
        token_budget -= n
        num_scheduled[req.id] = n

    # 阶段二：新请求（发生抢占时通常跳过，避免本步计划被搅乱）
    while token_budget > 0 and len(self.running) < self.max_num_seqs:
        req = self.waiting.peek()
        cached = self.kv_cache_manager.get_computed_blocks(req)   # 前缀缓存
        n = min(req.num_tokens - cached, token_budget)
        ...
        self.running.append(req)
        token_budget -= n

    # 阶段三：交给执行层
    return SchedulerOutput(num_scheduled_tokens=num_scheduled, ...)
```

### 4.2 用一组数字走一遍

约束：`max_num_batched_tokens = 4096`；三个请求 R1(prompt 3000)、R2(prompt 100)、R3(prompt 5000)。

| step | 发生了什么 | 本步 token |
| --- | --- | --- |
| 1 | R1 prefill 3000；R2 prefill 100；R3 只剩 996 → **切块** | 4096（满） |
| 2 | R1 decode 1；R2 decode 1；R3 继续 prefill 4004（算完） | 4006 |
| 3 | 三条都 decode，各 1 | 3 |

三个现象都在表里：**预算打满**、**长 prefill 被切块**、**最后 90 个 token 预算被浪费**（因为没有别的请求了）。

**这张表是理解一切调度策略的母版**：所有策略都是在改这个填法。

## 5. 上下游契约

### 5.1 上游：谁在调它

```
EngineCore 主循环（进程 B）
  ├─ scheduler.schedule()                      ← 本文主角
  ├─ model_executor.execute_model(scheduler_output)
  └─ scheduler.update_from_output(scheduler_output, model_output)
```

`schedule()` 与 `update_from_output()` 是一对：前者分配，后者回收。

### 5.2 请求状态机

```
        ┌─────────┐  准入   ┌─────────┐  完成  ┌──────────────────┐
新请求 → │ WAITING │ ─────► │ RUNNING │ ─────► │ FINISHED_STOPPED │
        └─────────┘         └─────────┘        │ FINISHED_ABORTED │
             ▲                   │             │ FINISHED_LENGTH  │
             │    抢占/暂停       │             └──────────────────┘
             └───────────────────┘
                  PREEMPTED

特殊态：WAITING_FOR_REMOTE_KVS（PD 等远端 KV）
        WAITING_FOR_STRUCTURED_OUTPUT_GRAMMAR（结构化输出编译中）
```

### 5.3 下游：`SchedulerOutput` 里到底有什么

| 字段 | 含义 | 谁消费 |
| --- | --- | --- |
| `num_scheduled_tokens` | 每请求本步算几个 | runner 的 `_prepare_inputs` |
| `scheduled_new_reqs` | 新请求的完整信息（prompt、block_table、采样参数） | runner 建请求状态 |
| `scheduled_cached_reqs` | 老请求的增量（新 token id） | runner 续算 |
| `total_num_scheduled_tokens` | 本步总 token 数 | runner 定 batch |
| `scheduled_spec_decode_tokens` | 投机解码的草稿 token | 采样验证 |
| `num_common_prefix_blocks` | 前缀共享的 block 数 | KV 管理 |
| `finished_req_ids` / `preempted_req_ids` | 结束/被抢占的请求 | runner 释放状态 |
| `kv_connector_metadata` | PD 分离的 KV 搬运指令 | KV connector |

### 5.4 `update_from_output` 做什么

1. 把采样的 token 追加到请求
2. 判断是否结束（stop string / max_tokens / abort）
3. 释放结束请求的 KV block
4. 更新 `num_computed_tokens`
5. 把完成的请求放进 `finished_req_ids`

**调度器的正确性 = `schedule()` 的分配 与 `update_from_output()` 的回收必须对得上账**，尤其是 block 的引用计数。

## 6. 十个核心机制

### 6.1 准入与并发槽（`max_num_seqs`）

限制同时在跑的请求数。它保护的是**延迟**（batch 越大 TPOT 越长）和**显存**（每个请求都要一份 KV）。
调大：吞吐↑、TPOT↑。典型取值：在线服务 32–256，离线批量可以更大。

### 6.2 token 预算（`max_num_batched_tokens`）

一个 step 的总 token 上限，直接决定"这一步的 GEMM 有多大"。
调大：吞吐↑、TTFT↓（排队少）、TPOT↑（单步变长）、显存峰值↑。

> 代码里有两个名字：`self.max_num_scheduled_tokens`（本步实际可用，可能被 PP/投机调整过）和
> `self.scheduler_config.max_num_batched_tokens`（配置上限，投机场景还要扣掉 draft 槽位）。
> 读代码时不要把它们当成同一个数。

### 6.3 Chunked Prefill

**问题**：一个 32K 的 prompt 如果一次算完，会把这一步的 TPOT 顶到几百毫秒，所有正在 decode 的请求都遭殃。
**做法**：把它切成若干块，每步只算一块。
**代价**：这个请求自己的 TTFT 变长。
**参数**：`long_prefill_token_threshold`（超长就切）、Ascend 的 `profiling_chunk_config`（按预测时延动态定块大小）。

这是**理解一切调度策略的原型**：牺牲一个请求的 TTFT，换所有人的 TPOT 稳定。

### 6.4 Prefix Caching

相同前缀（系统提示词、few-shot 示例、多轮对话历史）的 KV 直接复用。
实现上是一次哈希查表：命中多少 token，就从 `num_computed_tokens` 起算，跳过的部分不重算。
**代价**：哈希计算 + 查表（CPU 开销），以及 block 的引用计数管理。

### 6.5 Preemption（抢占）

**触发**：`allocate_slots` 失败。
**选择**：FCFS 下踢最晚到达的（浪费最少）；`policy=priority` 下踢优先级最低的。
**恢复**：v1 只做 **recompute** —— 释放 KV，请求回 waiting，将来重新 prefill（能命中前缀缓存的除外）。
**代价**：白算一遍，且表现为 TPOT 尖刺。**抢占率是调度健康度的核心指标。**

### 6.6 投机解码对预算的影响

投机解码让一个请求一步可能算 `1 + k` 个 token（k 是草稿数）。这带来两个变化：
- token 预算里要预留 `draft_slots`；
- 调度器必须保证草稿 token 与已有 token 的对齐，否则验证会错位。

本仓的 `num_spec_tokens_to_schedule` 就是干这个的（`scheduler_profiling_chunk.py:1105`）。

### 6.7 多模态的 encoder 预算

图像/视频要先过 encoder，产出 embedding 缓存。这会占独立的 `encoder_compute_budget` 和 encoder cache 槽位，
所以调度器对多模态请求有一整套额外检查（`_try_schedule_encoder_inputs`）。

### 6.8 异步调度（`AsyncScheduler`）

**问题**：`schedule()` 跑在 CPU 上，模型跑在 NPU 上，两者串行 = 白等。
**做法**：让调度领先执行一步 —— 发出 `SchedulerOutput` 后，立刻为"预期产出的 token"占位（`num_output_placeholders`），
不等模型结果就先调下一次 `schedule()`。
**代价**：状态滞后一步，所有涉及"结果"的判断都要用占位符校正。

本仓的 `XxxAsyncScheduler` 都是 `AsyncScheduler` + 某个同步调度器的 MRO 组合，
由 `AsyncScheduler` 提供占位符记账（见 `scheduler_profiling_chunk.py:1163` 的类注释）。

### 6.9 PD 分离

Prefill 节点和 Decode 节点分开部署：P 算完 prompt 把 KV 传给 D。
调度上的影响：
- D 节点要处理"KV 还没到"的等待态（`WAITING_FOR_REMOTE_KVS`）；
- KV 传输失败时要能回退重算 —— 这就是 `RecomputeScheduler` 的由来；
- 两侧的 budget 与超时策略要匹配，否则 D 会空转。

### 6.10 DP 负载均衡

数据并行下多个 rank 各自调度，快的等慢的 → 整体被最慢的拖住。
本仓有两种解法：
- **全局准入门**（`patch_balance_schedule.py`）：任一 rank 满了，所有 rank 停止准入；
- **跨 rank 快照**（`dyntra_lb_scheduler.py`）：交换各 rank 状态，planner 决定 admit / keep / pause，**不迁移请求**。

### 6.11 与图模式的耦合（Ascend 特有，必看）

调度器决定的 batch 形状（token 数、请求数）直接决定能不能命中已捕获的 ACL Graph：

- 形状命中 → 图回放，延迟低
- 形状不命中 → 退回 eager，延迟尖刺

所以 Ascend 上"调度抖动"的代价比 GPU 上更大。这也是为什么本仓要做：
- 把 batch padding 到 capture size（`_determine_batch_execution_and_padding`）
- uniform decode（让 decode 请求的 query 长度一致，形状可预测）
- 动态分块（让 prefill 块大小落在已捕获的档位上）

## 7. 指标：怎么知道自己调对了

| 指标 | 说明 | 恶化说明 |
| --- | --- | --- |
| TTFT | 首 token 延迟 | 排队久 / prefill 被切太碎 |
| TPOT / ITL | decode 每 token 间隔 | batch 太大 / prefill 混入 / 抢占 |
| tokens/s | 吞吐 | batch 太小 / 调度开销大 |
| goodput | 满足 SLO 的比例 | 策略与负载不匹配 |
| waiting / running 队列长度 | 排队与占用 | waiting 长期 > 0 且 running 未满 = 准入有问题 |
| KV 使用率 | block pool 占用 | 长期 > 90% → 很快要抢占 |
| 抢占次数 | preemption 计数 | 任何非零都值得警惕 |

**看指标的顺序**：先看 waiting 是否堆积（准入问题）→ 再看 running 是否打满（并发问题）→ 再看抢占（显存问题）→ 最后看 TTFT/TPOT 曲线（体验问题）。

## 8. 本仓调度器地图

上游只有一个 `Scheduler`；本仓按 `additional_config.scheduler_config` 选子类。
选择逻辑在 `platform.py:1457-1487`，配置定义在 `ascend_config.py:1630`。

| 调度器 | 场景 | 核心思想 | 与上游的关系 |
| --- | --- | --- | --- |
| `Scheduler`（上游） | 默认 | 先 running 后 waiting，FCFS | 基线 |
| `ProfilingChunkScheduler` | 需要精细控制 chunk | 启动时 profile 拟合延迟模型，运行时预测最优 chunk | **整段复制 `schedule()`** |
| `RecomputeScheduler` | PD 分离的 D 节点 | KV load 失败时回退重算 prefill | **整段复制** |
| `ShortRequestFirstScheduler` | P 节点 / 混合 | 短请求优先 + 老化，防长请求饿死 | **不覆盖 `schedule()`**，只换 waiting 队列 |
| `BatchJobAwareScheduler` | 离线批任务 | LPT 长作业优先 + KV 预留 | 包 `super().schedule()` |
| `BalanceScheduler` | PD-mixed，大 DP | 全局准入闸门 | **整段复制**（monkeypatch 形式） |
| `DyntraLBScheduler` | PD 的 D 节点，单机多 DP | 跨 rank 快照 + planner | **整段复制** |

**重要认知**：前四个"整段复制"是为什么本仓调度代码难维护的根因 —— 它们复制的是某个上游版本的函数体，
上游后续的新逻辑（比如 SWA 重放）它们收不到，只能整体关掉（见 `platform.py:1493-1503` 的注释）。

| 扫 running | 320–582 | 算 `num_new_tokens` → `allocate_slots` → 失败则抢占 |
| 扫 waiting | 584–1000+ | 前缀缓存 → chunk 切分 → 准入检查 |
| 组装 | 1113–1160 | `SchedulerOutput(...)` |

三处最能体现设计意图的代码：

```python
# :365  本步该给它算多少 —— 全部调度的核心公式
num_new_tokens = (request.num_tokens_with_spec + request.num_output_placeholders
                  - request.num_computed_tokens)
if 0 < self.scheduler_config.long_prefill_token_threshold < num_new_tokens:
    num_new_tokens = self.scheduler_config.long_prefill_token_threshold   # 长 prefill 切块
num_new_tokens = min(num_new_tokens, token_budget, input_budget - draft_slots)

# :459  先要显存，再决定算 —— 这个顺序解释了为什么显存压力表现为延迟抖动
new_blocks = self.kv_cache_manager.allocate_slots(request, num_new_tokens, ...)

# :482  抢谁：FCFS 踢最晚来的，代价最小
preempted_req = self.running[-1]
```

而最该记住的是 264 行往下那段上游注释：

```
There's no "decoding phase" nor "prefill phase" in the scheduler.
Each request just has num_computed_tokens and num_tokens_with_spec.
At each step, the scheduler tries to assign tokens so that
each request's num_computed_tokens can catch up its num_tokens_with_spec.
```

**调度器眼里没有 prefill/decode 阶段，只有"还欠多少 token"。** decode = 欠 1，prefill = 欠 prompt_len，
chunked prefill = 先还一部分，前缀缓存 = 已还过一部分，投机解码 = 欠 1+k。同一套代码，只是数值不同。

## 12. 八个常见坑

1. **把 step 当成 request**：调度是毫秒级的 step 循环，一个请求跨几百上千 step。看指标要区分 per-request 与 per-step。
2. **混淆三个 token 计数**：`num_computed_tokens` / `num_scheduled_tokens` / `cached_tokens`，混用会得出"调度器有 bug"的错误结论。
3. **只读 Ascend 副本，不读上游**：副本是某个上游版本的快照，改之前先确认它对齐的是哪个 tag。
4. **以为调度器会"迁移"请求**：本仓的负载均衡是"准入/暂停"，不是把运行中的请求搬到别的 rank。
5. **忽略图模式耦合**：Ascend 上调度抖动会导致图命中率下降，性能下降幅度远大于 GPU。
6. **在抢占分支上加同步操作**：`schedule()` 是 CPU 热路径，任何 `item()`/IO 都会放大成延迟。
7. **以为 async 调度"免费"**：它把正确性复杂度从"同步"换到了"占位符记账"，调试难度上升。
8. **改完只看吞吐**：不看 TTFT/TPOT 和抢占率，很容易做出"吞吐涨了但体验崩了"的改动。

## 13. 自测十题

1. 一个 step 里 token 预算还剩 500，来了个 prompt 2000 的请求，会发生什么？
2. 为什么先扫 running、后扫 waiting？
3. 抢占之后那个请求的 KV 去哪了？它重新进来要算什么？
4. `max_num_seqs` 从 8 调到 64，哪个指标先变差？为什么？
5. 前缀缓存命中 1000 token，`num_computed_tokens` 和 `num_scheduled_tokens` 分别怎么变？
6. chunked prefill 保护了谁、牺牲了谁？
7. 异步调度为什么需要 `num_output_placeholders`？
8. PD 分离后，D 节点为什么可能需要"重算 prefill"？
9. 为什么 Ascend 上调度抖动比 GPU 上更致命？
10. 一个请求从 WAITING 到 FINISHED，会经过哪些调度器方法？

### 答案要点

1. 不加进本步（或只加 500 个 token 的 chunk），剩余部分留到下一步；具体取决于 chunked prefill 是否开启。
2. 已在跑的请求被饿一步会直接体现为 TPOT 抖动，且 decode 只需 1 token，性价比高；保住在跑的优先于接新的。
3. KV 被释放，请求回到 waiting；重新进来时从头 prefill（除非前缀缓存命中）。
4. TPOT 先变差（单步要算的请求变多），随后可能因显存不足出现抢占，导致 TTFT 和 TPOT 一起恶化。
5. `num_computed_tokens` 直接跳到 1000（视为已算），`num_scheduled_tokens` 只算真正要算的新 token。
6. 保护了同 batch 的 decode 请求（TPOT 稳定），牺牲了长请求自己的 TTFT。
7. 因为调度领先执行一步，`update_from_output` 还没回来，必须先用占位符把"预期产出"记账，否则预算会算错。
8. KV 传输可能失败或超时，D 节点必须能自己重算以保证正确性（同时避免无限等待）。
9. 调度决定的 batch 形状不命中已捕获的 ACL Graph 时会退回 eager，延迟尖刺远大于 GPU 的 kernel 重选。
10. `schedule()`（准入）→ `update_from_output()`（回填/结束）→ 若被抢占还有 `_preempt_request()`；结束时进 `finished_req_ids`。
