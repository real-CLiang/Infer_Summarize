# vLLM Ascend 请求全流程（端到端）

> 三份文档的分工：`ONBOARDING.zh-CN.md` 是地图（有什么），
> `WALKTHROUGH-inference.zh-CN.md` 是路线（怎么读代码），
> 本文是**一页纸总览**（请求从进来到出去经过了什么）。

## 1. 全景图：一次请求跨三个进程

```
  客户端
    │  POST /v1/chat/completions（流式）
    ▼
┌─ 进程 A：API server ──────────────────────────────────────────────┐
│  tokenize → EngineCoreRequest → ZMQ 发往进程 B                     │
│  （本仓在这一点上只挂了 connector / model 注册，主流程是上游的）      │
└───────────────────────────────────────────────────────────────────┘
    │
    ▼
┌─ 进程 B：EngineCore ──────────────────────────────────────────────┐
│  ① 入队 waiting                                                   │
│  ② Scheduler.schedule()  →  SchedulerOutput                       │
│  ③ KVCacheManager.allocate_slots()  分配/复用物理 block            │
│  ④ 发 SchedulerOutput 给进程 C                                     │
└───────────────────────────────────────────────────────────────────┘
    │  SchedulerOutput（序列化）
    ▼
┌─ 进程 C：Worker × N ──────────────────────────────────────────────┐
│  ⑤ execute_model   前向 + logits                    → None        │
│  ⑥ sample_tokens   采样                            → ModelRunnerOutput │
└───────────────────────────────────────────────────────────────────┘
    │  ModelRunnerOutput {req_id: [token_ids], logprobs, ...}
    ▼
进程 B：update_from_output → 追加 token / 判停 / 释放 block
    │
    ▼
进程 A：detokenize → SSE 逐 token 推回客户端
    │
    └─ 未结束 → 回到 ②，下一轮（此时这条请求已是 decode）
```

**记住这条主干的形状**：`调度（B） → 执行（C） → 回填（B） → 输出（A）`，之后循环 ②→⑤→⑥ 直到结束。

### 为什么前向和采样要拆成两次调用

`execute_model` 返回 `None` 不是偷懒：它把「算完 logits」和「取走采样结果」**解耦**，让调度器可以在采样还没做完时就准备下一拍（async scheduling），也能让 PP 的非末级 rank 直接返回中间张量、不参与采样。

## 3. 一层 decoder 内部

```
hidden_states [T, H]
  │
  ├─ input_layernorm ──────── AscendRMSNorm（torch.ops._C_ascend.*）
  ├─ q/k/v_proj ───────────── AscendLinear / 量化（W8A8、W4A8…）
  ├─ rotary ───────────────── npu_apply_rotary_pos_emb（或融合 pass 吃掉）
  ├─ Attention.forward ────── reshape_and_cache + PA/FIA + o_proj
  ├─ residual
  ├─ post_attention_layernorm
  └─ MLP 或 MoE
       ├─ dense：gate_up_proj → SwiGLU → down_proj
       └─ MoE  ：router → dispatch → grouped GEMM → combine
                 （可能融合成 MC2，通信藏在算子内部）
```

这一层里**只有 Attention 是本仓重写的**；其余靠「算子替换 + 图融合 pass」把上游层实现换成 NPU 版本。所以调 attention 相关问题去 `attention/`，调其余问题先看 `ops/` 和 `compilation/passes/`。

## 5. prefill 与 decode 是两种完全不同的负载

| | Prefill | Decode |
| --- | --- | --- |
| 每请求 token 数 | 多（prompt 或 chunk） | 1（投机解码时 1+k） |
| KV cache | 写 + 可能读历史 | 读历史 + 写当前 1 个 |
| 主要 kernel | FIA（带 mask / sparse_mode） | PA（`npu_paged_attention`）或 FIA |
| 瓶颈 | 计算（GEMM） | 访存（KV 带宽） |
| 形状稳定性 | 差（每请求不同） | 好（每请求 1 token） |
| 图模式 | 常 PIECEWISE，或按 chunk 大小分档 | 常 FULL |
| 混合批 | 两者可同批（ChunkedPrefill），A5 上会按 phase 拆两次 kernel | |

`attn_state` 的五个取值（`attention_v1.py:160`）就是用来表达这些组合的：`PrefillNoCache / PrefillCacheHit / DecodeOnly / ChunkedPrefill / SpecDecoding`。

## 6. 五条不变量（改代码前先确认有没有破坏）

1. `sum(num_scheduled_tokens) == total_num_scheduled_tokens`，且等于本轮 token 数。
2. `query_start_loc` 以 0 开头、单调递增，长度 = 请求数 + 1。
3. `slot_mapping` 的长度等于**实际** token 数，不含 padding。
4. TND 布局要求 `sum(actual_seq_lengths_q) == hidden_states.shape[0]`（padding 时靠补假请求满足）。
5. 图模式下所有长度必须从 `*_gpu` 取，不能读 Python 侧刚刷新的值。

前四条破坏任何一条 → kernel 报错（常见 561002）；第五条破坏 → 不报错但结果静默错误。

## 7. 不是每条请求都走的支线

| 特性 | 在流程里的位置 | 入口 |
| --- | --- | --- |
| PD 分离 | 阶段 ⑤ 之前/之后搬 KV | `distributed/kv_transfer/`、`kv_connector_metadata` |
| 投机解码 | ⑧ 之后多一步 propose，下轮多算 k 个 token | `worker/*/spec_decode/`、`sample/rejection_sampler.py` |
| 多模态 | ⑤ 之前插 encoder | `ec_manager/`、`_execute_mm_encoder` |
| LoRA | 线性层内切换 adapter | `lora/` |
| EPLB | 每步后重排专家 | `eplb/`、`distributed/eplb/` |
| 前缀缓存 | ② 之前命中，直接给 `num_computed_tokens` | 上游 + `patch_kv_cache_utils.py` |

## 8. 出问题时的定位顺序

1. **先确认是不是本仓的锅**：拿 `VLLM_USE_V2_MODEL_RUNNER=0/1` 各跑一次；两代表现不同 → 问题在 runner 层。
2. **看调度输入**：在 `worker.py:867` 打印 `scheduler_output`，确认 token 数、请求集合符合预期。
3. **看 metadata**：在 `attention_v1.py:332` 打印 `attn_state`、`seq_lens_list`、`actual_seq_lengths_q`；数值对不上就是 ②③ 的问题，不是 kernel 的。
4. **看 kernel 入参**：在 `attention_v1.py:912/1139` 打印 shape 与 block_table 行数——**FIA 报错的绝大多数原因是行数/长度与 batchSize 不匹配**。
5. **看回填**：`_bookkeeping_sync` 里 `_to_list` 前后各打一次，确认采样结果与请求的映射没串。

## 9. 一张图收尾

```
请求 ──► 调度（算什么）──► 执行（怎么算）──► 采样 ──► 回填 ──► 输出
           │                │
           │                ├─ 输入张量      「算什么内容」
           │                ├─ attn_metadata 「去哪读、用哪个 kernel」
           │                └─ ForwardContext「这一拍的全局上下文」
           └─ SchedulerOutput 「算谁的几个 token」
```

理解这条链上的**四个数据对象**（`SchedulerOutput` → 输入张量 → `AscendMetadata` → `ModelRunnerOutput`）如何在进程间流动，就理解了这个仓 80% 的设计。
