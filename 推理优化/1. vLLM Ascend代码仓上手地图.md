# vLLM Ascend 代码仓上手地图

> 面向新加入、做推理性能优化的工程师。基于本地仓库快照实测（`main` 分支，`v0.19.1rc1-3061-g041cfb328`）。

## 0. 一句话定位

vLLM Ascend 是 vLLM 的**硬件插件（out-of-tree platform plugin）**，不是 vLLM 的 fork。

vLLM 通过 `setup.py` 里的 entry point 发现它，把 `NPUPlatform` 注册成"当前平台"；此后设备管理、worker、attention backend、custom op、量化方法全部通过 vLLM 的**扩展点**注入。只有当上游 vLLM 没有可用扩展点时，才在 `vllm_ascend/patch/` 里打补丁。

理解这一点，等于理解了这个仓 80% 的设计取舍：

- 上游演进快 → 需要 patch 层兜底，也需要 `vllm_version_is()` 版本分支。
- 只做"插件" → 目录结构天然按 vLLM 的扩展点切分（platform / worker / attention / ops / quantization）。

版本对齐信标：`.github/vllm-main-verified.commit`（main 车道）和 `.github/vllm-release-tag.commit`（release 车道）。改代码前先看当前分支对齐的是哪条车道。

## 3. 启动时序：从 `vllm serve` 到 kernel

这是**最值得先背下来**的一条链路，出问题时按图索骥。

```
pip install  ->  setup.py entry_points
                    ├─ vllm.platform_plugins: vllm_ascend:register
                    └─ vllm.general_plugins: register_connector / model_loader / model / service_profiling
   │
vllm serve / LLM(...)
   │
   ├─(1) vLLM 加载 plugin，得到 "NPUPlatform"
   │      -> vllm_ascend/__init__.py: register()
   │
   ├─(2) NPUPlatform.pre_register_and_update(parser)      platform.py:316
   │      ├─ adapt_patch(is_global_patch=True)  -> import vllm_ascend.patch.platform
   │      ├─ 注册 Ascend 量化 config（ascend / compressed-tensors / fp8 / modelopt_mxfp8）
   │      └─ 扩展 CLI choices（--quantization ascend、--kv-cache-dtype 新 dtype）
   │
   ├─(3) NPUPlatform.check_and_update_config(vllm_config)  platform.py:489  ★核心
   │      1. apply_v2_model_runner_config_patch()  (决定 V1/V2 runner)
   │      2. 日志配置
   │      3. 一批 _validate_*（parallel / pcp-dcp / engram / aux_output / indexer）
   │      4. maybe_auto_detect_quantization() + kv cache dtype 校验
   │      5. _fix_incompatible_config()          (改上游默认值以适配 NPU)
   │      6. init_ascend_config()                (解析 --additional-config)
   │      7. _update_compilation_modes()         (ascend_config -> vllm_config)
   │      8. _setup_compile_backend()            (cudagraph sizes / compile backend)
   │      9. _setup_worker_and_scheduler()       (worker_cls / scheduler_cls / custom_ops=["all"])
   │     10. _set_pytorch_npu_alloc_env()
   │
   ├─(4) Worker 进程: NPUWorker.__init__()                worker/worker.py:160
   │      ├─ 重放 V2 patch（子进程拿到的是 pickled config，platform 钩子不跑）
   │      ├─ adapt_patch()  -> import vllm_ascend.patch.worker
   │      ├─ ops.register_dummy_fusion_op() / register_ascend_customop()
   │      └─ init_ascend_config() + check_ascend_device_type()
   │
   ├─(5) load_model()  ->  initialize_kv_cache()  ->  compile_or_warm_up_model()
   │      (KV cache 分配/重排、ACL Graph 捕获、warmup)
   │
   └─(6) 循环 execute_model()                              model_runner.py:2339
          _prepare_inputs()  ->  _build_attention_metadata()  ->  forward  ->  sample_tokens()
                                      │                         │
                                      └─ AttentionMetadataBuilder└─ ACLGraphWrapper replay
```

关键点：**platform 钩子只在主进程跑，worker 进程拿到的是 pickle 过的 `VllmConfig`**。所以任何"影响 worker 行为"的 config/补丁，必须在 `NPUWorker.__init__` 里幂等地再执行一次（这就是 `apply_v2_model_runner_config_patch()` 在 `__init__.py`、`platform.py`、`worker.py` 三处都出现的原因，注释写得很明白）。

## 4. 六个必须先懂的机制

### 4.1 插件注册面（5 个 `register_*`）

| entry point | 函数 | 作用 |
| --- | --- | --- |
| `vllm.platform_plugins` | `register()` | 返回 `"vllm_ascend.platform.NPUPlatform"`，vLLM 据此实例化平台 |
| `vllm.general_plugins` | `register_connector()` | KV / EC 连接器 + weight transfer engine |
| `vllm.general_plugins` | `register_model_loader()` | netloader / rfork 加载器 |
| `vllm.general_plugins` | `register_model()` | `vllm_ascend/models/__init__.py` 里的模型注册表 |
| `vllm.general_plugins` | `register_service_profiling()` | 服务级 profiling 配置 |
| `ms_service_metric.providers` | `get_metric_provider()` | 对接 MindStudio 指标 |

前四个里除 `register_model` 外都会先调 `_ensure_global_patch()`，因为 **engine-core 子进程里 e2e conftest 的钩子不生效**，全局 patch 必须靠插件入口兜底。

### 4.2 Patch 机制（读 `patch/__init__.py` 就是读设计史）

- `patch/platform/`：主进程补丁，由 `pre_register_and_update()` → `adapt_patch(is_global_patch=True)` 触发。
- `patch/worker/`：worker 进程补丁，由 `NPUWorker.__init__` → `adapt_patch()` 触发。
- `patch/__init__.py`（≈1665 行）**不是代码，是索引文档**：每个 patch 都写了「补了什么 / 为什么 / 怎么补 / 上游 PR / 未来怎么删」。

仓库的原则（`docs/source/developer_guide/Design_Documents/patch.md`）：

1. 能不打补丁就不打；
2. 加了补丁必须写移除计划；
3. 随时欢迎删补丁。

实操建议：**遇到"这段行为为什么和上游不一样"，先去 `patch/__init__.py` 全文搜关键词**，90% 能找到答案和上游 issue 链接。

### 4.3 硬件画像 `HardwareProfile`（一套代码，四种芯片）

`vllm_ascend/device/hardware.py` 定义 `AscendDeviceType`：`A2`(910B) / `A3`(910C) / `_310P`(300I Duo) / `A5`(950)。

`device/hardware_profile.py` 把芯片映射成一组 `HardwareCapability` 枚举（约 60 个开关）+ 几个 family 枚举：

- `AttentionBackendFamily`：`STANDARD` / `COMPATIBILITY`（310P 走后者，直接切到 `vllm_ascend._310p.*`）
- `QuantizationBackendFamily`、`DeviceAdaptorFamily`、`WeightLayoutPolicy`、`MoECommPolicy`、`DeviceAddressingMode`、`CPUBindingMode`

代码里到处是这种写法：

```python
if get_current_hardware_profile().supports(HardwareCapability.FP8_ATTENTION):
    ...
```

**新增特性时，正确姿势是"加一个 capability + 在四个 profile 里声明支持与否"，而不是到处写 `if device_type == A2`。**

### 4.4 两级配置体系

| 层 | 载体 | 谁来读 |
| --- | --- | --- |
| 上游层 | `VllmConfig`（model / parallel / cache / scheduler / compilation / speculative…） | vLLM 与 vllm-ascend 共用 |
| 插件层 | `AscendConfig`：`--additional-config '{"key": value}'` 解析而来，嵌套 `AscendCompilationConfig` / `EplbConfig` / `SchedulerConfig` / `KVPPConfig` / `RlConfig`… | `get_ascend_config()` |

规矩：**不要在业务代码里自己 `json.load` additional_config**，一律 `get_ascend_config().xxx`；新增字段要在 `ascend_config.py` 的 dataclass 里声明并加校验。

构建类开关（`SOC_VERSION`、`COMPILE_CUSTOM_KERNELS`、`CMAKE_BUILD_TYPE`…）才放 `envs.py`，且必须写在 `env_variables` 字典的注释里（AGENTS.md 硬性要求）。

### 4.5 两代 Model Runner（V1 / MRV2）

| | V1 | V2（MRV2） |
| --- | --- | --- |
| 路径 | `worker/v1/model_runner.py`（≈6.6k 行，单文件） | `worker/v2/model_runner.py`（≈1.4k 行）+ `attn_utils` / `aclgraph_utils` / `pcp_manager` / `input_batch` / `model_states` / `spec_decode` 模块化 |
| 状态 | 全功能，兜底 | **默认启用**，重构中，持续迁移 |
| 选择 | `mrv2_utils.use_v2_model_runner()` 决定 | |

选择逻辑（`mrv2_utils.py`）：

- `VLLM_USE_V2_MODEL_RUNNER` 环境变量优先级最高；
- 否则默认 V2，但命中黑名单回退 V1：pooling KV、VL encoder 分离/encoder-only/encoder graph、`draft_window_size`、`enable_dsa_cp`、suffix / ngram / draft_model 投机、dflash2 图模式、p-eagle（`parallel_drafting`）。

**新人注意**：改 model runner 前先确认目标功能跑在哪一代上。同一个 bug 常常要改两处（`worker/v1/` 和 `worker/v2/`），仓库里 `patch/worker/patch_v2/patch_model_runner.py` 就是干这个的。

### 4.6 Attention 后端矩阵

`NPUPlatform.get_attn_backend_cls()`（platform.py:251）用三个维度选后端：`use_mla` / `use_sparse` / `use_compress`。

| 条件 | 后端类 | 文件 |
| --- | --- | --- |
| 优先尝试（非 PCP） | `AscendFABackend` / `AscendFlashAttentionBackend` | `attention/fa3_v1.py` / `fa_v1.py` |
| MLA | `AscendMLABackend` | `attention/mla_v1.py`（≈3.2k 行） |
| GQA/MHA 常规 | `AscendAttentionBackend` | `attention/attention_v1.py`（≈1.7k 行） |
| MLA + sparse | `AscendSFABackend` | `attention/sfa_v1.py` |
| MLA + compress | `AscendDSABackend` | `attention/dsa_v1.py`（≈2.6k 行） |
| 310P 兼容 | `AscendAttentionBackend310` | `_310p/attention/attention_v1.py` |

同一个文件里的骨架（以 `attention_v1.py` 为例，值得完整读一遍）：

- `AscendAttentionBackend`（:77）：`get_name()` / `get_builder_cls()` / `get_impl_cls()` / `get_kv_cache_shape()`
- `AscendAttentionState`（:160）：Prefill / DecodeOnly / ChunkedPrefill / SpecDecoding
- `AscendMetadata`（:169）：seq_lens、block_table、slot_mapping、attn_state…
- `AscendAttentionMetadataBuilder`（:242）：**性能热点**，把 scheduler 输出翻译成 kernel 参数
- `FIAParamProvider` / `PAParamProvider`（:518/:553）：FusedInferAttention / PagedAttention 两套参数风格
- `AscendAttentionBackendImpl`（:564）：`forward()` 里按 state 分派到不同算子

## 5. 一次 decode step 的数据流（性能视角）

以 V1 runner 为例，`execute_model()`（`worker/v1/model_runner.py:2339`）内部：

1. `_update_states()`（:993）：同步 scheduler 的请求增删、block table、slot mapping。
2. `_prepare_inputs()`（:1378）：拼 `input_ids` / `positions` / `seq_lens`，决定 padding，处理 spec decode 元数据——**CPU 侧大头，注意别在这里加同步点**。
3. `_build_attention_metadata()`（:3754）：按 layer 构建 `AscendMetadata`，区分 prefill/decode、是否图模式。
4. `_model_forward()`（:3501）：进入模型 forward；若开启图模式，实际是 `ACLGraphWrapper` replay（`compilation/acl_graph.py`）。
5. `sample_tokens()`（:2874）→ `_sample()`：sampler / rejection sampler（投机采样）。
6. `_bookkeeping_sync()`（:3102）：回填 CPU 侧统计——**这里最容易埋 `tensor.item()` 的性能坑**。

配套的大块逻辑都在 `model_runner.py` 后半段：`initialize_kv_cache()`（:4899）、`_allocate_kv_cache_tensors()`（:5299）、`_reshape_kv_cache_tensors()`（:5748）——KV cache 的物理布局（page-strided、NZ、C8/MXFP、MLA 单块 cache）全在这几千行里，改 KV 相关特性必读。

## 6. Kernel 层三个入口

| 类型 | 位置 | 说明 |
| --- | --- | --- |
| C++ / ACLNN 自定义算子 | `csrc/` + `vllm_ascend/ops/register_custom_ops.py` | 暴露为 `torch.ops._C_ascend.*`；`CMakeLists.txt` 构建；`COMPILE_CUSTOM_KERNELS=0` 时是 `dummyFusionOp` 桩 |

| ACLNN 融合算子（可选） | `vllm_ascend/ops/packaged_attention.py`、`_cann_ops_custom/` | 走包内 aten 通路 |

## 7. 图捕获与编译链路

- `compilation/acl_graph.py`：`ACLGraphWrapper` / `ACLGraphEntry` / `GraphParams`——捕获与回放的核心，`_updatable_graph_replay` 是"参数可更新图"的关键。
- `compilation/breakable_aclgraph.py`：可打断图（Ascend 上默认 opt-in，`VLLM_USE_BREAKABLE_CUDAGRAPH=0`）。
- `compilation/compiler_interface.py` + `graph_fusion_pass_manager.py`：torch.compile backend 与 PassManager 挂钩。
- `compilation/passes/`：图级融合（`qknorm_rope_fusion_pass`、`norm_quant_fusion_pass`、`muls_add_pass`、`mm_reduce_scatter_fusion_pass`）。
- 设计文档：`Design_Documents/ACL_Graph.md`、`npugraph_ex.md`。

图模式的三个坑：capture size 对齐（`update_cudagraph_capture_sizes()`）、`_dummy_run()` 与真实 forward 必须同构、动态 shape 下必须用"可更新图"而不是重新捕获。

## 10. 开发工作流

```bash
# 1. 环境：Linux + 驱动 + CANN + torch_npu（Windows/macOS 只能做 lint 和 CPU UT）
#    推荐直接用 main 分支镜像：quay.io/ascend/vllm-ascend:nightly-main
pip install -r requirements-dev.txt
SOC_VERSION="ascend910b1" pip install -e .    # 源码安装，会编译 csrc

# 2. 格式化 + lint（提交前必跑，含 markdown）
bash format.sh ci

# 3. 提交（必须带 sign-off）
git commit -s -m "fix: xxx" -m "why xxx"
```

## 12. 常见坑清单

1. **热路径禁止 `tensor.item()`**：设备张量 `item()` 会触发 NPU→CPU 同步，可能卡死 `AsyncScheduler`。必须用时要有理由并注明（AGENTS.md 明文警告）。
2. **patch 的幂等与顺序**：`spawn` 出来的子进程会重新 import 打补丁；多个 patch 抢同一个入口（如 `run_engine_core`）时，顺序错了就是隐式 wrapper 链，`patch_engine_core.py` 就是为此统一收口的。
3. **版本分支**：`vllm_version_is("0.31.0")` 之类判断遍布代码，改上游行为前先确认当前对齐哪个版本（`.github/vllm-main-verified.commit`）。
4. **310P 是完整分支**：改标准路径要考虑 `vllm_ascend/_310p/` 是否有对应实现；`AttentionBackendFamily.COMPATIBILITY` 会直接切走。
5. **三套配置别混**：CLI（`VllmConfig`）/ `--additional-config`（`AscendConfig`）/ 环境变量（`envs.py`），各有归属。
6. **custom op 可能是桩**：没编译 kernel 时 `torch.ops._C_ascend.*` 是 `dummyFusionOp`，UT 里常见，别误判为 bug。
7. **KV cache 布局有多种**：page-strided / NZ / C8-MXFP / MLA 单块，任何"假设 shape"的改动都可能只覆盖一种。
8. **图模式不是免费**：改 forward 要同时考虑 `_dummy_run()`、capture size 对齐、参数可更新性。
9. **文档构建也要过**：改文档跑 `make -C docs html`，CI 还有 doctest（`tests/e2e/doctests/`）和 linkcheck。
