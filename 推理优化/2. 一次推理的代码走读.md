# 一次推理的代码走读（vLLM Ascend）

> 配套 `ONBOARDING.zh-CN.md` 使用：那份给"地图"，这份给"路线"。
> §3 用"进程"视角重讲了启动时序，建议与 ONBOARDING §3 对照着读。
> 所有行号基于本地 `main` 快照核对；代码变动后请以 `grep` 结果为准。

## 0. 读之前先接受三个事实

1. **这个仓不拥有 HTTP、调度器、模型定义、采样器主体**。这些在上游 vLLM。本仓拥有的是：平台（`platform.py`）、worker（`worker/worker.py`）、runner 的覆写/钩子、attention 后端、算子与量化方法。
2. **一次 forward 的数据契约只有两样**：`SchedulerOutput`（调度器给的"这一步算哪些 token"）和 `ForwardContext.attn_metadata`（runner 造好的"每个 attention 层怎么算"）。
3. **两代 runner**：默认 V2（`mrv2_utils.py:130`），但 V2 是 `GPUModelRunner` 的子类，编排逻辑在上游；V1（`worker/v1/model_runner.py`）仍保留全量实现，是读懂"完整流程"最省力的入口。

> 这三个"事实"里最反直觉的是跨进程：**平台钩子只跑在构造 config 的那个进程里，worker 拿到的是序列化后的副本**。§3 专门讲这件事，读 Hop 1、Hop 2 卡住时先跳到那里。

```python
    key=key_to_cache, value=value_to_cache,
```

然后按状态分派（`attention_v1.py:1297`）：


```python

    block_table=attn_metadata.block_tables, context_lens=attn_metadata.seq_lens, out=output)

    query=query, key=key, value=value,
    atten_mask=attn_metadata.attn_mask, block_table=block_table,
    input_layout="TND", block_size=block_size,
    actual_seq_lengths=attn_metadata.actual_seq_lengths_q,
    actual_seq_lengths_kv=actual_seq_lengths_kv,
    num_key_value_heads=self.num_kv_heads, num_heads=self.num_heads, scale=self.scale)
```

两个必须懂的布局概念：

- **TND**：`[总 token 数, head, dim]` 的扁平布局，batch 边界靠 `actual_seq_qlen` / `actual_seq_kvlen` 描述，不靠 shape。
- **block_table + slot_mapping**：KV cache 是分页的。`slot_mapping` 是"这个 token 的 K/V 写进哪个物理槽"，`block_table` 是"这条请求的第 i 个逻辑页对应哪个物理页"。前者管写，后者管读。

`DeviceOperator` 不是类，是别名（`device/device_op.py:2102`）：

```python
DeviceOperator: type["BaseDeviceAdaptor"] = get_device_adaptor()
```

A2/A3 用 `BaseDeviceAdaptor`（`device_op.py:50`）、A5 用 `A5DeviceAdaptor`（`1027`）、310P 用 `Ascend310PDeviceAdaptor`（`2031`）。想加硬件差异，扩展这里，而不是在 attention 里写 `if device == ...`。

## 3. 启动时序：三个进程视角

> ONBOARDING §3 那张图难读，是因为它同时画了**时间**（启动到第几步）、**空间**（在哪个进程里跑）、**对象**（改的是哪个配置）三个维度。补上"进程"这一维，图就散了。

### 3.1 默认拓扑是三个进程

`vllm serve` 起来之后不是一个进程：

```
进程 A：API server（你敲命令的那个）
  argparse → 构造 VllmConfig → 序列化发出去
  ★ 平台钩子 (1)(2)(3) 只在这里跑
        │  序列化的 VllmConfig（msgpack / pickle）
        ├──────────► 进程 B：EngineCore —— 调度器 + KV 管理器
        │            只跑 global patch；决定"这一步算谁的哪几个 token"
        └──────────► 进程 C：Worker × N —— NPUWorker → ModelRunner
                     每张卡一个；★ (4)(5)(6) 只在这里跑
```

### 3.2 一条铁律，三条推论

> **模块级状态不跨进程，只有序列化对象跨进程。**

B 和 C 都是 `spawn` 出来的全新解释器。你在 A 里通过 `import` 打上的 monkey patch，在 C 里**一个字节都不存在**。推论：

1. 配置能过去（`VllmConfig` 是 dataclass，可序列化），补丁过不去（它只是内存里的函数指针）。
2. 凡是影响 worker 行为的补丁/类属性，必须在 C 里**幂等地重放**。
3. A 里改配置的机会只有一次，就在 (3)，改完立刻打包发走。

> 注意例外：单卡 `UniProcExecutor` 或 `VLLM_ENABLE_V1_MULTIPROCESSING=0`（InprocClient）时进程会合并，platform 的补丁恰好对 worker 可见。但仓库代码一律按**最坏情况（spawn）**写，所以重放逻辑始终存在且幂等——这正是它可以安全重复调用的原因。

### 3.3 六个阶段按进程重排

| 阶段 | 进程 | 时机 | 输入 → 输出 | 为什么必须在这里 |
| --- | --- | --- | --- | --- |
| (1) 发现插件 | A | `import vllm` 时 | 包元数据 → 类路径字符串 | vLLM 得先知道"用哪个 Platform"才能干活，此时它连硬件都没摸 |
| (2) `pre_register_and_update` | A | argparse 已建好、**parse 之前** | parser → 改过的 parser | 要往 `--quantization` / `--kv-cache-dtype` 的 `choices` 里塞值，parse 之后再塞没用 |
| (3) `check_and_update_config` | A | config 构造完、**序列化之前** | `VllmConfig` → 改过的 `VllmConfig` | A 里最后一次能改 config 的机会 |
| (4) `NPUWorker.__init__` | C | 每卡一次 | 反序列化的 config → 可用 worker | (2)(3) 的补丁在 C 里不存在，必须重放 |
| (5) load → 量内存 → KV cache → warmup | C | 每卡一次 | 权重 → 模型 + KV cache + 已捕获的图 | 需要真设备 |
| (6) `execute_model` 循环 | C | 每步 | `SchedulerOutput` → token | 同上 |

(A) 里那 10 个小步骤（`_fix_incompatible_config`、`init_ascend_config`、`_setup_worker_and_scheduler`…）**全部只是改数据**，不加载权重、不碰设备。这是它 2000 行却不显重的原因。

(5) 的顺序有讲究：KV cache 能开多大取决于"权重加载完还剩多少显存"，所以必须 `load_model` → `determine_available_memory`（`worker.py:653`）→ `initialize_kv_cache`；而 ACL Graph 捕获要用真实 cache 形状，只能排最后。

一句话记：**A 决定用什么零件，B 决定算谁，C 负责算。**

### 3.4 三个代码证据

**证据 1｜(2) 为什么必须在 parse 前**（`platform.py:325`）

```python
quant_action = parser._option_string_actions.get("--quantization")
if quant_action and hasattr(quant_action, "choices") and quant_action.choices:
    if ASCEND_QUANTIZATION_METHOD not in quant_action.choices:
        quant_action.choices.append(ASCEND_QUANTIZATION_METHOD)
```

`--quantization ascend` 能用，就是因为这行在 parse 前把 `"ascend"` 塞进了合法值列表。

**证据 2｜(4) 为什么必须重放**（`worker.py:178`）

```python
# Worker processes receive a pickled VllmConfig, so the platform config
# hook (NPUPlatform.check_and_update_config) never runs here. Re-apply the
# Ascend V2 model runner overrides ... Idempotent.
apply_v2_model_runner_config_patch()
sync_v2_extra_kwargs(vllm_config)
adapt_patch()
```

注释里那句 "the platform config hook never runs here" 就是整节的全部答案。

**证据 3｜EngineCore 也逃不掉**（`patch/__init__.py:568`）

```
In multiprocessing `spawn` mode the child process starts a fresh
interpreter, so monkey-patches applied in the parent are lost unless the
subprocess entry point re-applies them before any `EngineCore` is created.
```

所以 `patch/` 是三个落点而不是两个：`patch/platform/`（进程 A）、`patch/worker/`（进程 C）、`patch_engine_core.py`（进程 B）。`apply_v2_model_runner_config_patch()` 出现三次，是这条铁律的直接后果，不是冗余。

### 3.5 为什么这些方法在本仓找不到调用点

`check_and_update_config`、`pre_register_and_update`、`get_attn_backend_cls` 在本仓**只有定义、没有调用**——因为它们是**框架回调**：`NPUPlatform(Platform)`（`platform.py:93`）覆盖基类方法，调用方在上游 `vllm` 包里。

| 方法 | 谁调用 | 时机 |
| --- | --- | --- |
| `pre_register_and_update` | vLLM 构造 argparse 之后 | parse 前 |
| `check_and_update_config` | 上游 `VllmConfig.__post_init__` | config 构造完 |
| `get_attn_backend_cls` | vLLM 解析 attention 后端时 | config 校验（进程 A，用于 block_size 对齐，见 `platform.py:400`）+ 构造 attention layer（进程 C）都会调 |

注意最后一行：**同一个钩子可能在两个进程里各被调一次**，而且两边的上下文不同（A 里只有 config，C 里有真实设备）。调试时看到"这个方法进了两次"不要惊讶。

在仓库里 grep `check_and_update_config` 会得到 100+ 命中，但生产代码**一处调用都没有**，全是定义、测试（`tests/ut/test_platform.py` 里手动调）和文档。**"只剩测试在调"就是调用方在框架侧的信号。**

要确认上游调用点，二选一：

```bash
# 有 vllm 源码时（预期命中 vllm/config/vllm.py 与 vllm/platforms/interface.py）
python -c "import vllm, os; print(os.path.dirname(vllm.__file__))"
grep -rn "check_and_update_config" <上一步打印的路径>
```

```python
# 没有源码时：运行时打印调用栈
from vllm_ascend.platform import NPUPlatform
import traceback
_orig = NPUPlatform.check_and_update_config
NPUPlatform.check_and_update_config = lambda vc: (traceback.print_stack(), _orig(vc))[1]
```

同类问题还有第四种形态：`torch.ops._C_ascend.*` 找不到定义，因为它在 `csrc/` 里用 `TORCH_LIBRARY` 注册。

### 3.6 自测三题

1. 我要加一个 `--ascend-enable-xxx` 开关 → 改 **(2)**，因为要动 argparse。
2. 我要在 worker 里换 sampler 实现 → 打 **`patch/worker/`**，靠 `NPUWorker.__init__` 的 `adapt_patch()`。
3. 我在 `platform.py` 里设的模块级全局变量，worker 能读到吗 → **不能**。跨进程只有两条通道：`VllmConfig` 和 `AscendConfig`（`--additional-config`）。

### 3.7 一眼验证

```python
import os
print("check_and_update_config pid=", os.getpid())   # platform.py:489 开头
print("NPUWorker.__init__  pid=", os.getpid())        # worker/worker.py:161 开头
```

跑一次 `vllm serve`，会看到**两个不同的 pid**。把"顺序"变成"空间"，这张图以后就不会再看糊涂。

## 4. 三个数据结构

**`SchedulerOutput`**（上游）：`num_scheduled_tokens`、`scheduled_cached_reqs`、`scheduled_spec_decode_tokens`、`total_num_scheduled_tokens`。只描述"这一步算谁、算几个 token"。

**`AscendMetadata`**（`attention_v1.py:169`）：每层一份。

| 字段 | 含义 | 谁在用 |
| --- | --- | --- |
| `attn_state` | PrefillNoCache / PrefillCacheHit / DecodeOnly / ChunkedPrefill / SpecDecoding | 分派 kernel |
| `actual_seq_lengths_q` | TND 的 query 边界（Python list） | FIA |
| `seq_lens` / `seq_lens_cpu` | 每请求 KV 长度 | PA / FIA |
| `block_tables` | 逻辑页 → 物理页 | PA / FIA |
| `slot_mapping` | token → 物理槽 | `reshape_and_cache` |
| `query_start_loc_gpu` / `seq_lens_gpu` | 设备侧长度源，图内刷新 | 图模式下唯一可信来源 |

最后一条是最容易踩的坑：**ACL graph 重放只重放设备操作**，capture 之后 Python 侧再刷新手写的 buffer 不会执行。所以图内后端必须从 `*_gpu` 取数。

**`ForwardContext`**：`set_ascend_forward_context()`（`ascend_forward_context.py:115`）除了挂 `attn_metadata`，还塞了 `moe_comm_type`、`capturing`、`in_profile_run`、`num_tokens`、`sinks` 等一批 Ascend 私有字段，模型层靠 `get_forward_context()` 读。

## 6. 五个常见误读

1. **"vllm-ascend 是个 fork"**——不是。它靠 entry point 注入平台，模型 forward 直接用上游的。
2. **"platform 里改的配置 worker 一定看得到"**——不一定。worker 进程拿到的是 pickle 的 config，且 patch 要重放。
3. **"metadata builder 只是拼参数，不耗性能"**——它每步都跑，且有 `.tolist()` 和 H2D，是 CPU 侧大头。
4. **"图模式下还能读 Python 侧变量"**——不能。图内只重放设备操作，长度要从 `*_gpu` 取。
5. **"`torch.ops._C_ascend.*` 报错就是 bug"**——没编译 kernel 时它是 `dummyFusionOp` 桩，UT 环境正常。
