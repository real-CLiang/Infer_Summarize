0.2 一句话总览

结论先行：预训练造「通才」，后训练造「会用工具、会思考的专才」，推理优化让这个专才「又便宜又快」——在这四层技术栈里，唯一能把单位成本降一个数量级的地方，是推理层。

先把两笔账的直觉建立起来。显存只花在四个地方：权重、KV cache（KV 缓存）、激活、碎片；时延只花在三个地方：排队、prefill（预填充）、逐个 token 的 decode（解码）。第 4 章会把这两句话变成可手算的公式——这也是它占了全书约 40% 篇幅的原因。

你现在不必记住公式，只需养成一个工作习惯：遇到「慢」和「炸显存」，先算账，再谈技巧。绝大多数性能事故不是缺一个高级特性，而是账没算清——比如按「激活参数」估权重显存，或者忘了 KV cache 会随并发线性涨。

第 1 章 大模型全景：预训练→后训练→推理部署→应用

本章要解决的问题一个模型从「一堆文本」到「你手机里能用的助手」，中间到底经过哪几道工序？为什么 2025 年之后突然开始流行「会想很久」的推理模型？

1.1 四层技术栈全景

结论先行：整个生态只有四层——预训练（造基座）、后训练（对齐并激发能力）、推理服务（把权重变成可计费的服务）、应用（Agent / RAG）——你 90% 的困惑都能定位到「我在改哪一层」，四层的堆叠关系与每层代表工具见图 1-1。

分层最大的好处是责任清晰：模型「不知道某件事」是第 1 层；「不听话、不按格式答」是第 2 层；「同样的模型别人比你便宜一半」是第 3 层；「答案对不对、要不要查资料」是第 4 层。你的战场在第 3 层，但必须看得懂第 2 层的产物：是不是 MoE、KV 用了多少组 GQA 或 MLA、有没有原生 FP8 权重、思考 token 预算给多大——它们直接决定显存与时延，第 4 章会逐条兑现。

1.2 预训练：next-token 预测与 scaling law

结论先行：预训练只做一件事——给定前文预测下一个 token；它决定模型的「知识上限」，也决定你要面对的硬件基本盘（参数量、层数、头数、词表大小）。

可以把它理解成「把整个图书馆压成一张概率表」：预训练在极大语料上最小化自回归交叉熵，产出基座模型（base model）——它会续写，但不会听指令、不会按格式回答。 预训练留下三样一直跟着你的东西：总参数量（权重显存）、层数与 KV 头数（KV cache 大小）、词表大小（embedding 与输出层 logits 的显存，也决定 token 化效率）。以 Qwen3.5（2026-02-16）为例：开放权重版 Qwen3.5-397B-A17B 总参 3970 亿、激活 170 亿，词表扩到 25 万，支持语言从 119 种增加到 201 种【已核实】。词表变大，同样的中文往往切成更少 token、计费更划算；但它抬高了输出层 logits 的显存——这是新手最容易漏算的一处。

还有一件事请现在就记住：「激活 17B」不等于「显存按 17B 算」——MoE 只激活少数专家，权重却必须全部驻留；激活参影响算力与带宽，不是静态显存（4.2 节用显存账本钉死）。

1.3 后训练：把基座变成助手

结论先行：后训练不增加知识，只改变「输出分布」——让它按指令回答（SFT）、按人类偏好取舍（DPO 一类）、按可验证奖励长链思考（RLVR）。

三段主线的一句话版本：SFT 教格式，偏好优化教取舍，可验证奖励 RL 教思考。第 3 章会拆开讲，这里只要建立直觉：后训练用少量高质量数据或可自动判分的环境，换取模型的一种行为方式，它不是知识来源。

为什么推理工程师要关心？后训练改变了负载形态：思考模型把输出从几百 token 拉到几千 token，而输出长度是成本表里最贵的一项——decode 每多一个 token，就要把全部权重再搬一次（流程见图 3-1）。

1.4 推理服务：一次请求从 GPU 到用户

结论先行：线上服务只交付两个数——首 token 多快（TTFT）、后面每个 token 多快（TPOT / ITL）；吞吐与成本都是这两个数的副产品。

餐厅的比方：prefill 是备菜，一次性把整张单子做完；decode 是上菜，一道一道往外端。严谨定义：prefill 对整段输入做一次前向，产出 KV cache 与首个 token，矩阵乘密集、算力受限；decode 每步只处理一个新 token，却要把全部权重读一遍，访存受限。4.1 节把它变成可计算的 roofline 判据。

三个口径先钉住（完整对照表见 4.1）：TTFT 是首 token 时延（含排队）；TPOT / ITL 分别是每 token 平均时延与相邻 token 间隔，跨引擎比较必须核对公式；goodput 是满足 SLO 的有效吞吐。

1.5 应用层：RAG 与 Agent

结论先行：应用层把「一次问答」变成「多次模型调用＋工具调用」，负载形态就从「单次长 prompt」变成「高频、短输出、带共享前缀」，优化重点随之改变。

以编码 Agent 为例：一个任务可能产生几十次模型调用，每次都要带上几乎相同的系统提示与工具定义——这就是共享前缀；输出通常很短，一次只改几行代码或调一个工具。这类负载最喜欢 prefix caching（省掉重复 prefill）和低延迟调度。反过来说，若仍按「单次长文本生成」配预算，钱就会花错地方。Agent 循环的完整形状见图 2-1。

1.6 推理模型（reasoning model）为什么出现

结论先行：预训练的数据红利变薄后，把算力从训练时搬到推理时（test-time compute）成了新路径——代价是输出 token 暴涨，优化目标从「省钱」变成「让长思维链跑得起」。

这不是推演：DeepSeek-R1 已证明纯 RL 能激发推理能力【已核实】；到 2026 年，思考又与工具调用缝在一起——DeepSeek V3.2（2025-12-01）自称首个把 thinking 融入 tool use 的模型【已核实，厂商自报】。「思考」不再是独立按钮，而是 Agent 循环里的一个动作。

1.7 2025–2026 格局速查与三条趋势

结论先行：模型半年一换代，但结构趋势只有三条：MoE 成默认、注意力变便宜、叙事从堆规模转向后训练＋Agent——这三条恰好就是推理优化的工作面。

三条趋势各一句话：① MoE 成默认（Qwen3.5 397B/17B、DeepSeek-V3.2 671B/37B、Kimi K2.5 1T/32B、Llama 4 都是稀疏 MoE【已核实】）→ 显存看总参、算力看激活参，瓶颈从算力转向显存与通信；② 注意力变便宜（DeepSeek Sparse Attention 与 Qwen3-Next 一类结构让 KV 不再严格随长度线性增长【演进中】）→ 长上下文更便宜，但容量公式要用模型实际结构来核；③ 叙事从堆规模转向后训练＋Agent（Qwen3.5 官方称增益主要来自 RL 与环境规模扩展【已核实】）→ 能力越来越依赖环境，而环境背后全是推理调用。

最后两条避坑：「1M 上下文」不等于长上下文能力（Qwen3.5 在 AA-LCR 上 68.7，低于 Gemini-3 Pro 的 70.7【已核实，厂商自报】——标称窗口与可用能力是两件事，选型要看基准而非宣传页）；MoE 的「激活 17B」不等于显存按 17B 算（4.2 节详述）。

3 句话记住

  • ① 四层栈：预训练定上限，后训练定行为，推理服务定成本，应用定负载形态。
  • ② 推理模型把算力搬到了推理时，所以「长输出」是 2026 年的常态负载。
  • ③ 三条结构趋势（MoE、更便宜的注意力、后训练＋Agent）就是推理优化的三个工作面。

第 2 章 Agent：让模型「做事」

本章要解决的问题Agent 和「会聊天的模型」差在哪一行代码？为什么 2026 年所有框架都在讲 MCP 和上下文工程？

2.1 Agent 循环：ReAct 骨架

结论先行：Agent 就是一个 while 循环——观察 → 思考 → 行动（调工具）→ 再观察，直到满足停止条件；框架差异都在三处：调度（谁选下一步）、记忆（看到多少历史）、错误处理（失败怎么办）。

严谨定义：Agent 是「以语言模型为策略函数、以工具调用为动作空间、以终止条件为停止规则的决策循环」。骨架来自 ReAct【已核实】；到 2026 年的关键变化是思考已是模型内建能力——不用手写「Thought:」模板，一次生成就把推理和工具参数一起吐出来。

代码 2-1｜ReAct 循环的最小骨架（伪代码）python
def run_agent(task, tools, max_steps=20, budget_tokens=200_000):
    history = [system_prompt(tools), user(task)]
    for step in range(max_steps):
        # 一次生成既产出「思考」也产出「要不要调工具」
        out = llm.generate(history, stop=["</tool_call>"])
        if out.is_final_answer:
            return out.answer
        try:
            result = tools[out.tool_name](**out.args)      # 行动
        except Exception as e:
            result = f"ERROR: {type(e).__name__}: {e}"      # 错误也要回灌给模型
        history.append(out.text)
        history.append(f"<observation>{truncate(result)}</observation>")
        if tokens(history) > budget_tokens:                 # 上下文预算兜底
            history = compress(history)                     # 保留目标+最近N步+关键结论
    return "达到步数上限，任务未完成"

三处细节决定 Agent 稳不稳：错误必须以可读文本回灌（看不到异常栈就会重复犯错）、观察结果必须截断（一次 grep 可能返回十万字符）、步数与 token 双预算（否则会把自己烧穿）。

2.2 工具调用（tool call）与 schema 设计

结论先行：工具调用是把自然语言意图翻成结构化参数，schema 质量决定成功率：参数越少、语义越单一、错误信息越可读，Agent 就越稳。

代码 2-2｜一个合格的工具定义json
{
  "name": "search_logs",
  "description": "在指定服务的最近 24 小时日志里按关键字检索，返回最多 20 条匹配行。用于定位线上报错。",
  "input_schema": {
    "type": "object",
    "properties": {
      "service": {"type": "string", "enum": ["gateway", "worker", "scheduler"]},
      "keyword": {"type": "string", "description": "只支持字面量匹配，不支持正则"},
      "limit": {"type": "integer", "minimum": 1, "maximum": 20, "default": 20}
    },
    "required": ["service", "keyword"]
  }
}

三个反例：参数过多（一次填 9 个字段，模型必然编造一两个）、错误不可读（返回 500 internal error，而不是「service 只允许 gateway/worker/scheduler」）、职责重叠（search_logs 与 query_logs 语义接近，模型随机挑一个）。

对推理读者还有一个约束：工具定义会占据 prompt——工具越多、描述越长，prefill 越贵；返回顺序不稳定还会让 prefix cache 失效（2.4 与 4.3 会回到这一点）。

2.3 上下文工程：记忆、压缩与 RAG

结论先行：Agent 的瓶颈通常不是「模型不够聪明」，而是上下文被塞满；2026 年的主流做法是分层（编排 / 检索 / 记忆）＋主动压缩折叠。

一个量化例子：Qwen3.5 的 search agent 在累计工具返回达到 256k 后会裁掉早期内容【已核实】——即便百万级窗口，工程上也不会一路塞到底，因为上下文长度是成本，不是免费额度，还会稀释注意力。

三层分工：编排层放目标、约束与当前计划（常驻）；检索层放本轮文档片段（用完即弃）；记忆层放跨会话事实（外部存储，按需检索）。RAG 的定位很朴素——把外部知识当作可检索的上下文，它解决「知识不在权重里」，不解决「模型不会推理」。

对推理侧的二阶影响：chunk 太大，每段都很贵；切得太碎，一次要检索十几段——两者都直接反映在 prefill 成本上。

第 3 章 后训练：把基座变成助手与推理者

本章要解决的问题SFT、DPO、GRPO 到底在改什么？为什么推理优化工程师也该懂一点后训练？

3.1 三段主线总览

结论先行：后训练是「教格式（SFT）→ 教取舍（偏好优化）→ 教思考（可验证奖励 RL）」三连；数据形态从「示范」变成「偏好对」，再变成「可自动判分的题目」。

一句话职责：SFT 学「照这个格式答」，偏好优化学「两个都不错时选哪个」，可验证奖励 RL 学「反复试，直到答案对得上」。训练集群的并行细节不在本书范围——3.6 节告诉你该用哪个工具。

3.2 SFT：最小可行配方

结论先行：SFT（Supervised Fine-Tuning，监督微调）是用示范数据把基座的输出分布掰到目标格式上，数据质量与去重比数量更关键。

三个要点：只对回答 token 算 loss（prompt 部分要 mask，否则会学成「复述问题」）；packing 与截断直接决定显存（多条短样本拼进一个序列能提吞吐，拼错了会串味）；去重比扩充便宜。经验值：1 万条干净、覆盖完整的样本通常比 10 万条噪声样本训得更稳——这不是论文结论，请以自己的评测集为准。

3.3 偏好对齐：RLHF(PPO) → DPO / ORPO / KTO

结论先行：RLHF 的三模型结构（策略、奖励、参考）成本高、易不稳；DPO 一类方法把「奖励模型」消掉，用偏好对直接优化策略——工程上更省，理论上更受限。

必须点出 DPO 的隐性代价：它把「人类偏好」压成了一个离线数据集，模型会去拟合这个分布的边角——表现就是答案变长、语气变怂、遇到边界问题就拒答。这也是为什么「能自动判分」的任务会转向下一节。

3.4 可验证奖励 RL：GRPO / RLVR / DAPO

结论先行：当任务能自动判分（数学答案、单元测试、格式校验），就可以丢掉人类偏好、直接用可验证奖励做 RL；GRPO 用组内相对优势替代 critic，把显存与工程复杂度一起降下来。

代码 3-1｜GRPO 的一次更新（伪代码）python
for batch in loader:                      # 每批是若干道题

    rollouts = [engine.generate(p, n=G, temperature=1.0) for p in prompts]  # 每题采 G 条

        adv = [(r - mean) / (std + 1e-6) for r in rew]

三个名词一次讲清：RLVR（RL with Verifiable Rewards）是「奖励来自可验证判定器」这类方法的统称；GRPO（Group Relative Policy Optimization，组相对策略优化）出自 DeepSeekMath（arXiv 2402.03300），用同题采样的组内均值/方差做基线，省掉与策略同规模的 critic；DAPO（arXiv 2503.14476）用解耦裁剪与动态采样救长思维链训练的稳定性。DeepSeek-R1（arXiv 2501.12948）则证明纯 RL 就能激发推理，不必先做大量 SFT【已核实】。

必须写的避坑：校验器有噪声，也会被「钻空子」。2026 年已有工作系统审视 RLVR 的 verifier 噪声与奖励黑客问题（arXiv 2610.17824）【演进中】。所以「有 verifier 就万事大吉」是错的——你还得防它被优化目标本身骗过去。

3.5 蒸馏与合成数据

结论先行：蒸馏（大模型产思维链、小模型学）与合成数据，是把一次昂贵 RL 的成果批量复制的手段，也是当前开放权重小模型推理能力的主要来源。

R1 之后的标准做法：用强模型在可验证任务上大量采样，筛出「答案正确且过程合理」的轨迹，再拿去做 SFT 或拒绝采样微调。Qwen3.5 的另一条路径是把 RL 的环境规模做上去——官方称用百万级 Agent 环境做 RL【已核实】，这提示环境本身成了新的 scaling 维度，而环境里跑的全是推理调用。

3.6 工具链与算力账

结论先行：后训练的工程难点是「训练与推理解耦」——rollout 用推理引擎、更新用训练框架；训推分离能拿到 3–5 倍的端到端加速（Qwen3.5 异步 RL 口径）【已核实】。

3 句话记住

  • ① SFT 教格式，DPO 教取舍，RLVR 教思考——数据形态决定方法选择。
  • ② GRPO 的关键是「组内相对优势」，省掉 critic 就省掉一大块显存。
  • ③ 后训练的瓶颈常在 rollout 侧，所以推理工程师和后训练工程师用的是同一批引擎。

第 4 章 推理优化

本章要解决的问题服务为什么慢、显存为什么炸、钱花在哪，以及按什么顺序拧旋钮。

4.1 一次请求的两条腿：prefill 与 decode

结论先行：prefill 是算力受限（compute-bound），decode 是访存受限（memory-bound）——这一条判断决定了你该量化权重还是改 kernel，几乎所有优化手段都是它的推论。

还是餐厅的比方：prefill 是备菜，一次把整张单子处理完；decode 是上菜，之后一道一道往外端。严谨定义：prefill 对整段输入做一次前向，产出 KV cache 与首个输出 token，矩阵乘维度大、算力打满；decode 每步只处理一个新 token，却要把全部权重从显存读到计算单元，算术强度极低。这两条腿在时间轴上的落点、以及四类显存占用随 batch 与序列长度怎么变，见图 4-1。

判据是算术强度（arithmetic intensity），即每读一个字节能换来多少次浮点运算：

式 (4-1)I=FLOPsBytes≈2×NactiveNtotal×w

其中 Nactive 是激活参数量、Ntotal 是总参数量、w 是每个权重的字节数（FP16 时 w=2）。稠密模型里 Nactive=Ntotal，于是 I≈2/w：FP16 下约 1 FLOP/Byte，而主流加速卡的算力带宽比在数百 FLOP/Byte 量级。低了一个数量级意味着 decode 永远在等显存，这就是它 memory-bound 的算术证明。MoE 例外：Nactive≪Ntotal，算力需求降了，但权重仍要全读——所以 MoE 的 decode 更缺带宽。

现场怎么判？跑一次压测，同时看两个利用率：SM（计算单元）利用率和显存带宽利用率。带宽顶到 80% 以上而 SM 闲着一半 → 访存受限，去量化权重、上投机解码、加 batch；两个都接近满 → 算力受限，去换更快精度（FP8/FP4）、上更好的 kernel（FlashAttention-3 / FlashInfer）、或加卡做 TP。这个判断只要 5 分钟，却决定后面一整天该干什么。

把这条判断变成可估的数：单步 decode 要读的字节数约为「全部权重 + 该 batch 的 KV」，于是

式 (4-1b)Tamortized≈权重字节数+KV 字节数×B有效带宽×B

左端是单 token 摊销时间 Tamortized（≈ 1 / 系统吞吐），不是单请求的 TPOT。分母乘 B 是因为一个 batch 的 KV 是一起读的，而权重只读一次却服务整个 batch——权重那部分被 B 均摊，这就是「加 batch 能提吞吐」的数学来源。注意这个口径：系统口径随 batch 变大而变小；单请求的 TPOT 由式 (4-3) 定义，batch 变大时基本不变、甚至因为每步时间也变长而变差，同时 TTFT 与显存越吃紧。把两者搞混，就会以为加 batch 能把单请求 TPOT 降几十倍。

三个时延指标的定义：

式 (4-2)TTFT=Tqueue+Tprefill+Tfirst decode
式 (4-3)TPOT=TE2E−TTFTNoutput−1

两个必须知道的坑：vLLM 的 TPOT 用的是式 (4-3) 这一口径，并与 ITL 分开统计，跨引擎对比前请核对公式【已核实】；被切块的 prefill 会把 prefill 时间摊进 ITL，所以开了 chunked prefill 之后 ITL 长尾会变好看，但不代表你变快了。

4.2 KV cache、显存账本与 PagedAttention

结论先行：显存只花在四个地方——权重、KV cache、激活、碎片；新手 90% 的 OOM 来自两个错误：按激活参数估权重，或者忘了 KV cache 随「并发 × 序列长度」线性增长。

类比：KV cache 是注意力层的笔记本——每读一个 token，就把它的 Key 和 Value 记下来，后面不用重算。严谨定义：自回归推理时把历史 token 每层的 K/V 张量缓存起来，避免重复计算，代价是显存随序列长度线性增长。

两笔账：

式 (4-4)Mweight[GB]=P×b8

其中 P 是参数量（按十亿计）、b 是位宽。MoE 的 P 必须用总参，不是激活参。

式 (4-5)MKV[GB]=2×L×Hkv×d×S×B×bytes

其中 L 是层数、Hkv 是 KV 头数（GQA 下远小于注意力头数）、d 是 head_dim、S 是序列长度、B 是并发数（batch）；系数 2 来自 K 和 V 各一份。bytes 是每个元素的字节数（FP16 时 2、FP8 时 1），算完除以 109 得 GB（除以 230 则为 GiB）——别把 B（并发数）当成字节单位读。

代码 4-1｜把两笔账算成一张表python
def ledger(P_b, bits, L, kv_heads, head_dim, seq, batch, kv_bytes):
    """返回 (权重GB, KV cache GB)。P_b 单位：十亿参数；按十进制 GB 算（÷1e9）。"""
    weight = P_b * 1e9 * bits / 8 / 1e9
    kv = 2 * L * kv_heads * head_dim * seq * batch * kv_bytes / 1e9
    return round(weight, 1), round(kv, 1)

# 示例模型：32B dense、61 层、GQA 8 组、head_dim 128（层数/头数为示例值）
for bits, kv_bytes, tag in [(16, 2, "FP16 权重 + FP16 KV"), (8, 1, "FP8 权重 + FP8 KV"), (4, 1, "INT4 权重 + FP8 KV")]:
    w, kv = ledger(32, bits, 61, 8, 128, 8192, 32, kv_bytes)
    print(f"{tag:22s} 权重 {w:6.1f} GB | KV {kv:5.1f} GB | 合计 {w+kv+4:6.1f} GB（+4 GB 工作区）")

最后一行是本章最值钱的一行：「激活 17B」不会让权重显存变小。激活参数只决定算力与带宽压力，权重按总参驻留。

三个最常见的误算，每个都能让估算差一倍以上：

  1. 用 max_model_len 乘并发估 KV。应按「实际平均输出长度 + 平均输入长度」，再留长尾余量；按上限估会把预算放大 4–8 倍，结论就是「什么都装不下」。
  2. 忘记 KV 的乘数效应。多轮对话、重试、beam、并发重放都会各自持有一份 KV，账本要按「活跃序列数」算，不是按「用户数」算。
  3. 忘记框架开销。CUDA Graph 捕获、通信 buffer、激活峰值、PagedAttention 的 block 取整都在吃显存；给 10%–15% 的余量是工程惯例，而不是保守。

另外一个结构性的杠杆：KV 头数由模型结构决定，你能改的只有位宽与调度。GQA 把 KV 头数从 64 降到 8，KV 就小 8 倍；MLA 把 KV 压成潜在向量，进一步降低常驻量，但让 KV 复用与迁移变复杂（4.6 节会看到引擎为此专门补了复用逻辑）。选模型时先看这两个结构参数，比后期调参有用得多。

PagedAttention 解决的是「碎片」这一项。类比：以前给每个请求预分配一段连续的 KV 显存，像给客人预留整张长桌，人没来齐也占着；分页之后按固定大小的 block 分配，像按座位号入座。严谨定义：把 KV cache 切成固定大小的 block，用逻辑块到物理块的映射表管理，从而消除预留浪费、支持不连续存放（SOSP'23，arXiv 2309.06180）。它把显存利用率从「按最大长度预留」提到「按实际使用」，但它不解决 prefill 重复计算，也不解决 ITL 抖动——那两件事分别归 4.3 节的另外两个旋钮。

4.3 调度三件套：continuous batching、chunked prefill、prefix caching

结论先行：三个旋钮各治一种病——continuous batching 治「GPU 等请求」的吞吐病，chunked prefill 治「长 prompt 卡住别人」的 ITL 抖动病，prefix caching 治「重复算同一段前缀」的浪费病。

continuous batching（连续批处理）：类比流水线拼单——不等整批做完，谁先结束谁下车，新车立刻补位。严谨定义：以迭代（每一步 decode）为调度粒度，动态加入新请求、移出已完成请求，使 batch 始终填满。

chunked prefill（分块预填充）：类比把一大锅汤分几次端——长 prompt 被切成若干块，与 decode 请求拼进同一个 batch。严谨定义：把一次 prefill 拆成固定 token 预算的多块，与 decode 混批执行，用吞吐换更平滑的 ITL（SARATHI，arXiv 2308.16369）。

prefix caching（前缀缓存）：类比复印机记住前 10 页——多请求共享的系统提示与工具定义只算一次。严谨定义：以 token 序列前缀为键缓存其 KV block，命中即跳过对应的 prefill 计算；vLLM 用哈希块做前缀复用，SGLang 用 radix 树做更细粒度的复用（含 session-aware radix cache 与 HiCache 分级卸载）【已核实】。vLLM 的 V1 架构用「每请求固定 token 预算」统一调度，prefill 与 decode 不再硬分阶段，因此能同时支持 chunked prefill、prefix caching 与投机解码【已核实】。

这三个旋钮不是独立的，改一个会牵动另一个。把 --max-num-seqs 从 64 提到 256，吞吐上去了，但 KV cache 的峰值也按 4 倍涨——显存不够时你会看到「提高并发反而触发抢占（preemption），吞吐掉回去」。把 gpu_memory_utilization 从 0.90 提到 0.95 能多吃一点缓存，但把余量吃光后，长 prompt 的激活峰值会直接 OOM。调参的正确顺序是：先固定显存预算，再定并发，再定分块大小。

排队时间也可以估算，用 Little 定律的直觉版：平均排队 ≈ 系统内请求数 ÷ 完成速率。当发现 TTFT 里排队占了大头（式 4-2 的三项要分开测），加卡或降单请求成本才有意义；如果排队很小而 prefill 很大，那就是前缀重复或 prompt 太长，该去开 prefix caching。

prefix cache 会失效，而且失效得很安静：chat template 里插入了时间戳或随机 ID、工具列表顺序每次不同（参见 2.4 节 MCP 的 tools/list 稳定顺序要求）、系统提示里带了「本次请求 ID」——这些都会让前缀在第一个 token 处就分叉，命中率直接归零。排查方法：把两次请求的 prompt 逐 token diff，看第一个不同的位置有多靠前。

4.4 量化：FP8 / NVFP4 / KV 量化

结论先行：量化是访存受限场景的第一优先级（decode 阶段），但它不是免费午餐：权重、激活、KV 三种量化对象的效果与硬件门槛完全不同。

FP8 已经是训练与推理的默认低精度：Qwen3.5 采用原生 FP8 流水线（敏感层运行时回落 BF16），官方称激活显存约降 50%、推理加速超过 10%【已核实，厂商自报】。NVFP4 从 Blackwell 一代引入，Blackwell Ultra 提供 15 PFLOPS 密集 NVFP4 算力，是同卡 FP8 的 3 倍【已核实】。KV cache 侧：vLLM 支持 FP8 KV，vLLM 0.32 在 ROCm 上增加了 4-bit 超低比特 KV，密度约为 FP8 的 2 倍【已核实】。

两句必须记住的话：低比特不是免费（FP8 要硬件支持，4-bit KV 要专门 kernel）；量化顺序建议先权重、再 KV、最后激活——因为权重直接决定能不能装下，KV 决定能开多少并发。

怎么验证量化没把模型弄坏：别只看困惑度。用你自己的任务集跑一遍，重点看三类容易崩的能力——长上下文一致性（把答案埋在第 20k token）、结构化输出合法性（JSON 能不能解析）、多步推理的正确率。KV 量化对前两项影响最大，权重量化对第三项影响最大。校准数据也要注意：用业务真实分布，不要用英文维基——校准集和线上分布不一致，是量化掉点最常见的原因。

一个可操作的最小流程：① 先试 FP8 权重（多数情况几乎无损）；② 显存还是不够，试 INT4 权重并逐层评估（敏感层保留高精度）；③ 并发上不去，再试 FP8 KV；④ 最后才碰 4-bit KV 与激活量化，并且必须重跑评测。每一步都记一组「吞吐 / TTFT / 任务分数」，否则你不知道自己换来了什么。

4.5 投机解码：EAGLE-3 与收益边界

结论先行：投机解码用「小模型起草 + 大模型验证」把 decode 的串行步数换成本更低、可并行的批量验证，收益与接受率、并发度强相关，不是恒定加速。

严谨定义：用一个草稿模型（draft）一次猜出 k 个 token，再用目标模型一次前向并行验证这 k 个位置，接受最长的一致前缀，从而把 k 步串行 decode 压成 1 步验证。EAGLE-3 的做法是放弃特征层预测、改为直接预测 token，并用 training-time test 扩充训练数据（NeurIPS 2025）【已核实】；它已经成为系统里的通用件，Qwen3.5 的异步 RL 框架里也用了投机采样【已核实】。

收益不用背公式，记住三个数：接受率 α、草稿长度 k、batch size。期望加速约等于「每步平均产出 token 数 ÷ 验证成本系数」，而 α 会随任务难度下降、k 过大时 α 迅速衰减。最关键的边界：当 batch 已经很大，decode 从 memory-bound 转向 compute-bound，验证步本身变贵，收益会趋零甚至为负【演进中】。

什么时候该开：低并发、交互式、输出较长且可预测（代码补全、格式化输出、结构化抽取）。什么时候别开：高并发批处理、输出很短、领域漂移导致 α 很低。

手算一下值不值：设接受率 α、草稿长度 k，验证成本约等于一次正常 decode step（乐观假设），每步期望产出为

式 (4-6)E[tokens/step]=1+α+α2+⋯+αk

取 α=0.7、k=4 得约 2.8 个 token/步（1+0.7+0.49+0.34+0.24≈2.77），理论加速约 2.8×；α 掉到 0.3 就只剩 1.4×——而系统复杂度、显存（要放草稿模型）、与大 batch 的冲突都是实打实的成本。α 是唯一值得你实测的数：在真实业务 prompt 上采样统计，低于 0.5 基本不用考虑。

两个相互作用要注意：投机解码会额外占用 KV 与计算，显存紧时可能先把你压垮；它与 chunked prefill 抢同一份 token 预算，同开要分别压测，收益不可简单相加。

4.6 并行策略与 MoE：TP / PP / EP / DP / SP

结论先行：并行是为了「放进显存 + 摊开算力」，代价是通信；MoE 时代 EP 的地位上升，wide-EP 成为服务大 MoE 的默认姿势。

三个 2026 年的实况：wide-EP 在 GB200 NVL72 上用 EP=64 服务 DeepSeek-R1，靠「每卡更少专家」缓解 GroupGEMM 瓶颈【已核实】；SGLang 的 Elastic EP 在 4 节点 32 卡上跑 DeepSeek V3.2，并支持部分故障容忍【已核实】；MLA 让 KV 复用变复杂，TensorRT-LLM 1.1 专门补了 MLA 的 KV cache reuse 与 host offload【已核实】。

一个反直觉的避坑：别把训练侧的 SP 当推理标配。vLLM 0.32 反而删除了 torch.compile 里的 sequence-parallel / AsyncTP pass【已核实】——推理侧的瓶颈是带宽与调度，不是那个并行度。

规模选择的四步流程（可直接照做）：

  1. 先算单卡能不能放下权重（式 4-4）；放不下就 TP 到 2–8 卡（单机内 TP，别跨机，all-reduce 太频繁）。
  2. 单机放不下 → 上 PP 跨机（切片放得下，但有流水线气泡，适合大 batch 离线）。
  3. 是 MoE → 必上 EP；专家越分散，all-to-all 越碎，每卡专家数别太少（wide-EP 的思路就是「适度分散 + 更少专家/卡」）。
  4. 副本数最后定：同一套并行配置复制 N 份做 DP，扩的是吞吐而不是单请求时延。

一句话记：TP 治「单层太大」，PP 治「整体太大」，EP 治「专家太多」，DP 治「流量太大」。四个词各对应一种「放不下」。

4.7 部署拓扑：PD 分离与 EPD 分离

结论先行：PD 分离把「算力受限的 prefill」和「访存受限的 decode」放到不同实例各自扩缩，能同时优化 TTFT 与 TPOT——但低 QPS 或短输出时，通信与空转吃掉收益。

严谨定义：PD 分离（prefill-decode disaggregation）把两阶段拆成两组实例，prefill 实例产出 KV cache 并通过高速互联传给 decode 实例；EPD 分离再把多模态 encoder 也拆出去。TensorRT-LLM 官方给的选型方法是：先按 TTFT 目标选 context server 的 TP/EP/DP/PP，再按目标 tok/s 选 generation server 的规模【已核实】。

NVIDIA 的 EPD 实测数据：文本请求的平均 TTFT 从 92.3 ms 降到 53.3 ms（−42.2%），但输出越长，端到端收益越小【已核实，厂商自报】——因为 decode 段一旦成为主导，省下来的那点 prefill 时间就被摊薄了。

判断标准很朴素：prefill 占总时延比重大、QPS 足够高才值得拆；低流量、短输出、单机装得下时，PD 分离只是多一条网络链路加运维复杂度。

4.8 引擎选型、指标口径与调优 checklist

结论先行：先量三件事（TTFT、TPOT、goodput），再按「瓶颈是显存还是算力」选旋钮，最后才考虑换引擎——换引擎是最后一招，不是第一招。整棵「症状 → 瓶颈 → 旋钮」的技术树，以及每个旋钮把吞吐-延迟曲线推向哪一段，见图 4-2。

选型经验（可直接照做）：单机、通用、要生态 → vLLM；前缀复用重、要结构化输出 → SGLang；已知模型、追极致性能、愿意做适配 → TensorRT-LLM；昇腾 → MindIE；端侧 / CPU → llama.cpp；跨机编排 → 在引擎之上加 Dynamo。

代码 4-3｜从逐 token 时间戳算三个指标 + SLO 判定python
def metrics(ts, e2e_slo_tpot=0.05):
    ttft = ts[0]
    tpot = (ts[-1] - ts[0]) / max(len(ts) - 1, 1)
    itl = [b - a for a, b in zip(ts, ts[1:])]
    p99 = sorted(itl)[int(0.99 * (len(itl) - 1))] if itl else 0.0
    return {"TTFT": round(ttft, 4), "TPOT": round(tpot, 4),
            "ITL_p99": round(p99, 4), "meets_slo": tpot <= e2e_slo_tpot}

# goodput = 满足 SLO 的请求数 / 总时长
def goodput(results, duration_s):
    return sum(r["meets_slo"] for r in results) / duration_s

30 分钟排障流程（照着走，别跳步）：

  1. 固定 workload：用固定的输入/输出长度分布与并发做基线，否则后面所有对比都不可信。
  2. 量三数两率：TTFT、TPOT、goodput，加上 SM 利用率与显存带宽利用率。SLO 先写成可判定的形式，如「TPOT ≤ 50 ms 且 TTFT ≤ 800 ms」（示例值）。
  3. 归类：显存不够 / TTFT 高 / ITL 抖 / 吞吐低 / 长上下文贵——只选一个主症状。
  4. 只拧一个旋钮，跑同一 workload，记录前后三个数与两个利用率。
  5. 没效果就回退，换下一个假设。任何一步都不要同时改两个参数，否则你永远不知道是谁起的作用。

最后一句纪律：任何吞吐数字都必须带条件——硬件型号、并行配置、输入/输出长度、batch、是否开 prefix cache，以及是「厂商自报」还是「第三方复现」。少写一个条件，这个数字就没有意义。

  • ③ 先量 TTFT/TPOT/goodput，再拧旋钮；换引擎是最后一招。

第 5 章 Agent-Team 是怎么做出来、怎么跑起来的

本章要解决的问题多 Agent 系统为什么容易「看起来很热闹、实际质量崩」？一个可靠的多 Agent 工程系统需要哪些机制？（本章每个机制都能在 DeepSeek Harness 的 AgentTeams 里找到真实对应物。）

5.1 为什么单个 Agent 不够

结论先行：单 Agent 的三个硬限制是上下文会被塞满、工作串行、失败无法被独立审查；多 Agent 的第一性收益不是「更聪明」，而是上下文隔离 + 并行 + 可审查。

一个具体反例：让一个 Agent 既要调研 6 个方向、又要写 1 万字、还要自查。结果几乎必然是「调研浅（每方向几百字就收尾）、写作长（凑字数）、自查放水」。这恰好对应上面三条限制——不是模型不行，是结构不对。

5.2 orchestrator-worker 架构

结论先行：经典结构是 captain（编排者）不亲自干大部分活：它拆任务、定依赖、派活、验收；member（工作者）在一次 attempt 内独立完成一件事并报告。Captain 的任务 DAG、调度器、质量门禁 review 回环与 mailbox 的完整走线见图 5-1。

为什么 captain 不自己干所有活：因为它自己也会被上下文塞满。captain 要装下「全部任务元信息 + 每个成员汇报 + 验收结论」，若同时还要写正文，写正文的细节就会挤掉协调所需的信息，两边都做不好。上下文隔离本身就是分工的理由。

类比「包工头与工人」，不是「全能老师傅」。严谨定义：orchestrator 只持有任务图与验收标准，worker 只持有单任务的输入与产出约束，两者通过结构化消息与共享文件系统交换结果。

取舍：orchestrator-worker 适合依赖复杂、需要返工的任务（「调研→写作→审校」里有回环）；流水线（pipeline） 适合阶段清晰、可并行的任务（同一份提纲并行生成 6 张图）。实战通常是混合：顶层用 DAG 编排，某一层内部用流水线——本书就是 t3（图）与 t4（文）在 t2 之后并行，再汇入 t5（构建）。

5.3 任务 DAG 与调度

结论先行：任务不是列表而是 DAG：dependencies 决定解锁顺序，调度器只派「依赖已全部完成」的任务；这让并行与正确性同时成立。

一个容易搞混的点：「认领」不等于「派活」——成员 claim 自己的 ready 任务并拿到 attempt，captain 用 reassign 才是真正派活并唤醒成员。

5.4 质量门禁与 review 回环

结论先行：可交付性的关键机制是独立 review + 硬门禁：review 类任务的完成条件不是「我写完了」，而是 verdict=pass；needs_revision / reject 必须带 findings 把任务打成 failed，并触发下一轮修复。

为什么必须独立：自评必然放水——写的人知道自己想说什么，读者只看得到写出来的字。所以规范里有条硬规矩：实现者不能给自己的产物判 pass。

findings 的写法决定回环效率：好的 finding 是「文件:行 + 问题 + 必须怎么改」（例：「04-inference.md:118：TPOT 公式漏了 -1，与 vLLM 口径不一致」）；坏的 finding 是「第 4 章写得不够好」——无法执行，只会让回环空转。

自动修复回路：review 失败 → 任务带 findings 回到 failed → 调度器重新派回原 owner（或改派）→ owner 在新 attempt 里逐条修 → 再次 review。闭环成立的前提是 findings 可执行、修复范围明确（inScope），否则每轮都会扩大战线。

还有一条纪律：Mail 不是正式 review——口头说「可以了」不能替代结构化 verdict，否则门禁就被绕过了。

5.5 attempt / 幂等 / 重试

结论先行：每次认领产生一个 attempt_id，所有更新都必须带它；任务被重派后旧 attempt 变成 stale，旧执行者的写入会被拒绝——这就是分布式系统里的 fencing token（栅栏令牌）。

三重收益：防并发写坏（两个执行者只有一个能落盘）、可安全重试（幂等：重放不产生两份产物）、可审计（哪次 attempt 产出哪个结果，一查便知）。

配套设计是「终态不可变，但证据可追加」：任务一旦 completed，结论不能被晚到的证据改写；想补充只能 append-only 地附在后面（如 evidence_note）。这看着啰嗦，实际是在保护评审结论的稳定性——否则任何人都能事后把「不通过」改成「通过」。

5.6 共享文件系统与写作用域

结论先行：多 Agent 共享一个工作区，冲突控制靠显式写作用域：每个任务声明自己能改哪些路径，产物按目录分家（research/、content/、diagrams/、输出目录）。

真实冲突：builder 拼 HTML 时发现正文有个错字，顺手改了 content/ 里的源文件——「构建产物」与「源文件」的对应关系就断了。正确做法是只读上游产物，要改就写进自己的输出目录并在报告里说明，让改动回到源文件 owner 手里。

还要区分两类共享：共享文件系统（内容，可读写）与共享状态（team.json、mailbox）——后者只能通过专用工具改，直接编辑等于绕过锁。

5.7 持久化、上下文隔离与失败恢复

结论先行：可靠性来自「状态外置」：团队状态写在 team.json、消息写在 mailbox，Agent 崩溃后重新读取即可恢复，不靠记忆。

三层隔离缺一不可：上下文隔离（每个 member 只看自己的信箱与依赖结果——省 token，也防污染）、文件隔离（写作用域决定谁能改哪棵树）、身份隔离（谁是 parent、谁能派活验收，由系统判定而不是 Agent 自称）。

失败恢复三件事：任务状态机（pending → in_progress → completed/failed，非法跳转被拒绝）、消息持久留存（未读不丢，重连即达）、幂等的重试语义（重派不产生重复产物）。
